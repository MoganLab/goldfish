## 2026-08-16 L2-1 编译 pass 管线验证
### What
L2（自研运行时替换 s7 eval）的第一步验证：自研编译 pass 能否处理 expander 产物。

1. 新增 `(goldfish compiler)` 库，定义 pass 管线框架：
   - `run-passes` : sexp (list pass) -> sexp，按序应用 pass
   - `compile-defs` : defs (list pass) -> defs，对展开后的库 defs 逐条应用管线
2. 实现第一个 pass `constant-fold`：递归折叠 `*foldable-functions*` 表中的纯函数调用
   （+ - * quotient remainder modulo abs min max expt 比较 字符串 字符 布尔等），
   参数全为常量时求值替换；quote/quote-syntax 内容作为数据永不进入。
3. 实现第二个 pass `simplify-if`：`(if #t t e)` -> t，`(if #f t e)` -> e，
   同时是第一个死代码消除。
4. 系统级等价验证：capture-library-cache 展开真实库（srfi-1）得到 48 个 defs，
   跑管线后 5 个 defs 被改写（`(if #f #f (if #f #f))` 死分支消除等），
   原/编译 defs 分别 eval 到独立 inlet，take/drop/append-map/find 调用结果一致。

### Why
L2 有三条路线（字节码 VM / 编译到 C / 解释器优化），共同前置是"自研代码能
处理 expander 产物"。本任务验证这条路径：pass 输入是 lower 后的核心 IR
（define/lambda/if/begin/set!/call-with-values/values/quote），输出仍可被 s7 eval，
不改动宿主求值器，风险低可回退。后续 L2 换后端时 pass 管线原样复用。

### How
- pass 输入层选择 lower 后的纯 sexp（datum 层）：scope 信息在展开时已固化，
  编译阶段不需要，且便于 write 验证与 diff 比较。
- `*foldable-functions*` 只收录**全函数且无副作用**的 primitive：折叠绝不允许把
  运行期错误变成编译期错误，也不允许改变可观察行为；`catch` 保护折叠本身
  （如 `(expt 2 100000)` 溢出），任何错误保留原形式。
- 折叠结果用 `self-evaluating?` 判断：数字/字符串/字符/布尔/空表/EOF 直接输出，
  其余（符号/列表/向量）用 `quote` 包装。
- 等价验证的关键：defs 的 define 名是带 scope 后缀的 gensym（如 `take:15`），
  编译不改名，因此原/编译 defs eval 到两个独立 `(inlet)` 后，同名绑定可直接
  构造调用比较——无需处理导出名到 gensym 的映射。

## 2026-08-16 L2-2 编译 pass 接入加载路径
### What
把 L2-1 的 pass 管线接入 `load-library!` 的实际 defs 求值路径，补齐
"展开 -> 编译 -> eval"闭环。

1. module.scm 新增 `optimization-level`（GOLDFISH_OPT_LEVEL 环境变量控制，
   -O0/1/2 惯例：0=不编译，1=默认，2+=预留扩展 pass 集；默认 1）。
2. 新增 `compile-defs-on-load`：eval defs 前调用。compiler 库**延迟加载**
   （load-library! 按需加载，非 expander 内核的一部分），用 catch 保护，
   加载失败则原样 eval（编译是优化，不是正确性要求）。
3. 接入点：`load-library-file-cached!` 的 `(for-each eval defs)` 前
   （缓存命中与缓存写入共用此函数）。无缓存路径（bootstrap）未接，
   因为该路径主要用于引导或首次编译，优化收益已被缓存路径覆盖。
4. 新测试：`tests/expander/compile-on-load-test.scm`（8 checks，验证 compiler
   库加载、defs 被改写、编译后库功能正常）、
   `tests/compiler/load-benchmark-test.scm`（运行期基准）。

### 实测数据
- 冷加载 (liii base + srfi-1)：编译开 453ms vs 编译关 482ms —— 编译开销可忽略
  （pass 在加载路径上近似免费）。
- 热加载：465-486ms，两模式一致。
- 运行期 take 20000x50 次：编译开 4.194s vs 编译关 4.208s（-0.34%）。
  srfi-1 多转发宿主 C 函数（take = g_take），真实收益需等 pass 对纯 Scheme
  实现的热点生效。

### 架构结论
- lib 层（module.scm 等）是运行时从源码加载的（install.scm 链），改动
  不需要重建 kernel-combined.scm artifact。
- compiler 库从 load-path 按需加载，与 expander 内核解耦；`import` 是 syntax
  不能在 lambda 内用，改用 `load-library!` + `module-ref` 运行时获取函数。

## 2026-08-16 SRFI-262 调查：可扩展模式匹配器与 nanopass
### What
调查 SRFI-262 (Extensible pattern matcher, Preston-Kendal 2025 draft) 能否辅助
提供 nanopass 框架的部分功能，并实测当前 `(liii match)` 的能力边界。

1. SRFI-262 仅在 coverage checking 设计说明中实质性提及 nanopass（Sarkar
   et al. 2005、Keep 2012）：作者认为可扩展匹配器可作为"带覆盖检查的匹配库"
   的后端目标，而覆盖检查正是 nanopass 精髓之一。其余引用仅参考文献。
2. SRFI-262 提供的 nanopass 式能力：`define-pattern-syntax` 为每个 IR 层定制
   解构器（`?` 谓词守卫 + `=>` 字段解构，`define-record-type+pattern-syntax`
   可自动生成）；`=>` 内部可跑任意递归（desugar 归一化）；Views 支持同一数据
   多视角；`seq`/`lset` 支持变长/无序子项；模式语法挂 identifier property
   （SRFI-213），词法作用域内可局部 shadow。
3. SRFI-262 不提供：穷尽性/覆盖检查（明确 out of scope）、IR 语言定义
   （define-language）、pass 边界校验——这些仍需自建。
4. 实测 `(liii match)`（WCS 风格）能力边界：
   - 可用：裸列表模式、`?` 谓词、`=` 解构、`and`/`or`/`not`（简单形式）、
     `$` 记录、`@` 字段、`***` 树、as-pattern `(and x pat)`。
   - 缺陷1：显式 `(list ...)` 模式展开期崩溃（match-extract-vars bug），
     需用裸列表 `(a b c)` 替代。
   - 缺陷2（关键）：模式关键字与 IR 节点名冲突——`define`/`lambda`/`quote`/
     `list`/`let` 等 WCS 关键字无法作为 IR 头匹配，而 core IR 恰恰全用这些
     名字，裸模式全被误解析，只能 `?`+`=` 逐节点解构（繁琐失声明性）。
   - 缺陷3：语法关键字写死，无 define-pattern-syntax 机制（不可扩展）。
   - 无 match-values：多值匹配需手写 call-with-values。

### Why
评估"用 match 辅助实现 nanopass 风格编译 pass"的可行性。结论：
`(liii match)` 不能直接匹配 core IR（关键字冲突）；SRFI-262 是匹配层的合适
候选（可扩展、支持 record），但需要 IR 改用 record 表示且需自建 IR 定义与
覆盖检查层。当前阶段 L2 继续扩展 pass 集优先于引入新匹配框架。

### How
- 误报教训：测试中 fallback clause 写成 `(quote no)` 会被 match 当作
  pattern 而非 body，导致大量虚假"崩溃"；正确写法是 `(_ (quote no))`。
- `(liii match)` 的 as-pattern 是 `(and x pat)` 而非 `&`。

## 2026-08-16 L2-3 pass 扩展：尾调用标记 + 死代码消除
### What
在 L2-1 的两个 pass 基础上扩展：

1. `tail-call-positions`：分析 pass，标记 lambda 体的所有尾调用位置
   （if 分支、begin 尾项、let 体尾项、call-with-values 的 consumer 调用），
   输出 `(tail-call <sexp>)` 包装。不改变求值语义，是 L2-3 后端
   （字节码 VM / 编译到 C）区分"跳转"与"压栈调用"的前置分析。
   导出供后端消费，不接入加载管线。
2. `eliminate-dead-defs`：死代码消除，删除未被任何幸存 def 引用的
   lambda 值 def（非 lambda 值可能有定义期副作用，一律保留），
   迭代到不动点。导出供 L2-3 使用，未接入加载管线（跨库 module-ref
   引用风险：被其他库引用的 def 无法在当前文件内判定死活）。

### 实测收益
- expander 内核：646 -> 636 形式，-3.2% 字符（删除 10 个未引用 def）。
- srfi-19：132 -> 130 形式，-0.24%。
- 真实库收益有限（内部引用密集），但 DCE 淘汰无用定义仍有价值。

### How
- DCE 修复的关键 bug：`collect-all-free` 曾用新列表替换 acc 而非追加
  （`(loop (cdr ds) (collect-free-symbols (car ds)))`），导致只保留最后
  一个 def 的 free 符号——表现为过度删除（expander 内核误删 232 个，
  实测 -76% 的假收益）。修复为 append 后真实收益 -3.2%。
- 尾调用标记的 `mark-body` 只处理 body 最后一个表达式；
  let/letrec* 的 body 是列表，标记位置在 body 上（多一层括号）。
- 测试：`tests/compiler/dce-tailcall-test.scm`（11 checks）。

## 2026-08-16 SRFI-262 核心子集实现（Racket 式扩展机制）
### What
实现 SRFI-262 可扩展模式匹配的核心子集，新库 `(goldfish match)`（goldfish/match.scm）。

1. 模式：`_` 通配符、`id` 变量、datum/quote、裸列表 `(a b c)`、`(list ...)`、
   `(cons a b)` 点对、`(vector ...)`、`(? proc subpat ...)`、`(=> proc ...)`、
   `(and ...)`、`(or ...)`、`(not ...)`。
2. 形式：match、match-lambda（按 arity 分组，运行时分派，无 case-lambda）、
   match-values、match-let、match-let*、match-define、if-match、
   define-pattern-syntax。
3. 扩展机制：**Racket 式**——define-pattern-syntax 定义 transformer 绑定，
   展开期用 syntax-local-value 解析绑定（binding-kind/binding-value），
   调用 transformer 重写模式。词法作用域天然隔离（shadow/import）。
4. 代码生成：CPS 式递归（gen*），每个模式生成嵌套 if/let 代码树；
   模式变量绑定卫生临时名（generate-temporaries），body 经 rename-body 替换。

### Why
- SRFI-262 是未来 Tree-IL IR 匹配层的候选（可扩展模式语法为 record 节点
  定制解构器）；先实现核心验证架构。
- 参考实现（extensible-match，3400 行）含完整决策树/seq/NFA，移植量大；
  核心子集先验证模式扩展机制与直接代码生成，seq/决策树后续可叠加。
  （注：`devel/1012/extensible-match/` 参考实现目录已于 2026-08-17 清理删除，
  其中含第三方代码与 submodule；如需查看可查 git 历史。）

### How
- 调试关键教训：
  1. syntax-form 只解一层，子元素仍是 syntax record；pattern 用
     syntax->datum 全量 datum 化，递归子模式用 syntax-form 的树。
  2. 宏 transformer 展开期引用库内函数可行（闭包捕获），但**前向引用**
     失败（函数须定义在 macro 之前）。
  3. fail continuation 传参：符号须包装成调用 `(,fail)`，不能裸传符号
     （否则生成引用而非调用）。
  4. expand-pattern 的 else：head 非符号（嵌套列表）也是 seq-list；
     点对用 (car form)/(cdr form) 而非 cadr/cddr。
  5. gen-vector* 须显式长度检查，否则长度不符时 vector-ref 越界。
- 无 case-lambda：match-lambda 按 arity 分组，生成
  `(lambda args (cond ((= (length args) n) (apply group-n args)) ...))`。
- match-define 顶层：展开为 `(begin (define tmp expr) (define v (match tmp
  (pat v) (_ error))) ...)`，多 define 顶层提升。

## 2026-08-16 SRFI-262 完整实现（扩展 match）
### What
从 git `f8b9bd66`（核心子集）重新应用 SRFI-262 完整功能：seq/seq*/seq/unordered
NFA 省略号、list/vector/cons*/lset 省略号、多值形式（match-let-values 等）、
quasiquote 模式、异常体系、match-ellipsis?。

### 疑似 expander bug 记录（待复核）
1. **宏体内 `let*-values`（syntax-rules）展开失败**：
   `(define-syntax m (lambda (stx) (let* ((expr ...)) (let*-values (((a b) ...)) ...))))`
   当宏体内已有名为 `expr` 的变量、且 let*-values 的 binding 表达式含 `expr` 时，
   报 `syntax-case: no matching clause`（binding 变量列表消失）。workaround：
   改用 `call-with-values`（普通函数调用）。
2. **并行 `let` 中 lambda 捕获同组绑定失败**：
   `(let ((a 1) (b (lambda () a))) (b))` 报 `unbound variable a`（标准 Scheme 应返回 1）。
   workaround：match 生成代码用 `let*`。
3. **嵌套 quasiquote 中内层 `(quote ...)`/splice 泄漏**：
   多级嵌套 quasiquote 构造时，内层 `,(var)` 在某些位置泄漏成字面 `(unquote var)`。
   例如 `(list '(begin ... ,ref))` 中 quote 内的 `,ref` 不 splice（这是 quote 语义，
   但易误用）；更隐蔽的是 `@(if partial? (list '(begin ... ,ref)) '())` 产生
   `(unquote ref)`。workaround：显式 `(list 'begin (list '%vm-step! 'vm ref))`。
4. **库内某定义结构损坏时，变量绑定静默失败但宏正常**：
   `match-let*-values` 的 `(let* ((first ...))` 缺 body 时，整个库的变量导出
   （%make-registers 等）引用报 `no-catch (#t)`，但 `match` 宏可用；且与任意
   第二库组合 import 失败。修复该定义后全部恢复。疑似 expander 对非法定义的
   报错被吞掉，导致后续绑定损坏。

5. **`(newline)` 后含 `(quote 复合)` 的表达式展开失败**（已最小复现）：
   ```scheme
   (import (scheme base))
   (newline)
   (display '(1 2 3))   ; 无输出，程序后续也被破坏
   ```
   受影响：`(display '(1 2 3))`、`(list '(1 2) 3)`、`(cons '(1 2) 3)`、
   `(list (quote a))`、`(quote (list 1 2))` 等；不受影响：`(car '(1 2))`、
   `(quote 5)`、`(if #t 1 2)`、`(+ 1 2)`。无 `(newline)` 前缀时全部正常。
   该 bug 使"display 结果 + newline"循环结构的测试文件（上一行 newline 后
   紧跟含复合字面量的 display）失败。workaround：用 `(liii check)` 的
   `check` 宏写测试，或把多个 display 合并到一行/最后统一输出。

6. **内部 `(let () (define-values ...) (define a t1))` 顺序错**（已最小复现）：
   ```scheme
   (let ()
     (define-values (t1 t2) (values 1 2))
     (define a t1)
     (+ a b))   ; b 报 `+ first argument, uninitialized`
   ```
   `(let () (define ...))` 展开成 letrec* 时，(define a t1) 在 t1 初始化前
   求值。标准 Scheme 应返回 3。workaround：match-letrec 改用
   `(define a (match init ((a) a)))` 形式（内部 define + match 表达式），
   避免内部 define-values。

## 2026-08-16 quasiquote 模式与 bounded NFA（扩展省略号）修复
### What
修复 `(goldfish match)` 的 quasipattern 与扩展省略号，参考实现测试
`extensible-match-test.sls` 的 Quasipatterns 段全部通过（除 syntax-violation
期望的 error 用例未移植）。回归 `match-srfi-262-test.scm` 保持 39/39。

### quasiquote 展开（expand-quasiquote）修复
1. `syntax-form` 泄漏 syntax 对象：`f` 改用 `(syntax->datum x)` datum 化，
   否则展开结果混入 syntax record，模式匹配失败。
2. 尾 unquote/unquote-splicing 检测：`(eq? (car rev) 'unquote)` 对 datum
   列表 `(unquote y)` 恒假；改为 `(pair? (car rev)) (eq? (caar rev) 'unquote)
   (pair? (cdar rev)) (null? (cddar rev))`，取值用 `(cadar rev)`。
3. proper list 精确匹配 vs dotted 尾匹配：`` `(,x 2 3) `` 用 `(list ...)`
   精确 3 元素；`` `(a . ,x) ``（reader 扁平化成 `(a unquote x)` proper）用
   `(cons* ...)` 尾匹配剩余，检测倒数第 2 元素是 unquote（`(eq? (cadr rev)
   'unquote)`）。
4. 多 subform unquote（`(unquote x y z)`）在 splicing 上下文拼接多个元素；
   空 unquote/unquote-splicing（`(unquote)`）等价于无元素。
5. `ell?` 扩展支持 datum `'...`；新增 `extended-ell?` 识别 `(... n)` /
   `(... n m)`；`has-ellipsis?` 和 `parse-seq-subpats` 支持 syntax 元素。
6. `flatten-sub-ellipsis`：把嵌套省略号元素 `(p ...)` 展平成 `p ...`，
   list/vector 分支统一走顶层省略号机制；cons* 尾不被 flatten。

### bounded NFA（扩展省略号 min/max）修复
根因：`expand-list-ellipsis` 把扩展省略号 `(... n)` 也包成 `(=> car ...)`
丢失省略号信息，导致 parse 全部 seq:one。改为
`(if (or (ell? p) (extended-ell? p)) p (list '=> 'car p))`。
`many-0-max` 指令顺序修正为 fork 在 test 前（continue/fork 目标按
`atp+2k+1` / `atp+2max`）；(min max) 分支 min 个强制 test 在 many-0-max 前。
修复后 `(... 0 1)` / `(... 1 2)` / `(... 2 4)` 等参考用例通过，
`` `(a (... 1 2) b) `` 也通过。

## 2026-07-30 第二个子任务：从 s7.c 拆出 s7_scheme_let.c / s7_scheme_let.h

### What
1. 新增 `src/s7_scheme_let.c`（约 1350 行）与 `src/s7_scheme_let.h`（44 个函数声明），
   从 `src/s7.c` 迁出 63 个代码区段：`g_unlet` 到 `g_is_defined` 的密集块，
   外加 `g_funclet` 与 `g_owlet`，涵盖 unlet / openlet / coverlet / varlet /
   cutlet / sublet / inlet / let->list / let-ref / let-set! / rootlet / curlet /
   outlet / symbol->value / symbol->dynamic-value / defined? / funclet / owlet
   及其私有辅助函数。`s7.c` 从 88327 行缩减到 87161 行。
2. `src/s7_internal.h` 追加约 260 行：迁移代码所需的宏（含 S7_DEBUGGING /
   WITH_GCC / REPORT_ROOTLET_REDEF 多分支变体）、`starlet_t` 枚举、
   外部全局变量与函数声明。
3. `s7.c` 中约 34 个 static 函数去 `static`（其中
   `add_slot_at_end`/`add_slot_checked_with_id`/`add_slot_unchecked`/
   `checked_slot_set_value`/`is_constant_symbol` 用 `extern inline` 保持内联），
   另去 `static` 5 个仅 S7_DEBUGGING 下编译的调试函数
   （`check_let_set_slots`/`set_opt2_1`/`set_opt3_1`/`gc_protect_2`/`unstack_1`）。
4. `xmake.lua` 注册 `src/s7_scheme_let.c`；release 与 debug（-DS7_DEBUGGING）
   两种模式均编译链接通过；`bin/gf test --all` 1492 项全部通过，
   20 个 let 测试文件单独运行也全部通过。

### Why
`s7.c` 是 88k 行的单体文件，按既定路线（0074 起陆续拆出 symbol/inexact/
continuation 等模块）继续拆分，let 相关函数是文档中规划好的下一块。

### How
- **边界判定靠引用计数**：用脚本统计每个候选函数被 s7.c 其余部分引用的次数，
  求值热路径函数（lookup、position_of、is_proper_quote、starlet 等，被引用
  数十到数百次）留在 s7.c，只迁出 20 个公开 let API 及其私有辅助。
- **`extern inline` 模式**：热函数在 s7.c 保留 `extern inline` 定义、
  在 s7_internal.h 放 `extern inline` 声明，TU 内仍内联、TU 间有外部符号。
- **H_/Q_ 宏留在 s7.c**：文档/签名宏虽定义在函数体内但作用于文件，
  s7.c 尾部的 defun 注册点仍在使用，迁移时只加注释标明函数已迁出。
- **`symbol_set_id` 的双形态**：release 下是宏、debug 下是函数，头文件需
  用 `#if S7_DEBUGGING` 镜像该结构，否则 release 链接报 undefined reference。
- **`make_integer`/`make_real` 例外**：s7.c 的快路径宏依赖 static 的
  `small_ints` 数组，s7_scheme_let.c 中直接
  `#define make_integer(Sc, N) s7_make_integer(Sc, N)`（函数内部有同样的
  小整数快路径），避免把 small_ints 暴露出去。

## 2026-07-29 第一个子任务：在 (liii base) 导出 20 个 let 相关函数并补齐文档与测试

### What
1. 在 `goldfish/liii/base.scm` 的 export 列表中新增 20 个 let 相关函数：
   `let?` `openlet?` `funclet?` （谓词）
   `curlet` `outlet` `rootlet` `owlet` `funclet` （环境获取）
   `inlet` `sublet` `varlet` `cutlet` `openlet` `coverlet` `unlet` （环境构造与操作）
   `let-ref` `let-set!` `let->list` （绑定访问）
   `symbol->value` `symbol->dynamic-value` （符号查找，`defined?` 此前已导出）
2. 在 `tests/liii/base/` 下为这 20 个函数各写一个文档化测试文件
   （文件名遵循 `gf doc` 的特殊字符映射规则：`?` → `-p`、`!` → `-bang`、
   `->` → `-to-` 等），共新增 20 个测试文件、111 个 check。
3. 执行 `bin/gf doc --build-json` 重建函数索引，确认
   `bin/gf doc funclet`、`bin/gf doc let-set!`、`bin/gf doc symbol->value`
   等命令都能正确显示 `(liii base)` 下的文档和测试用例。
4. `bin/gf test --all` 共 1492 项全部通过（其中新增 111 个 check）。

### Why
这些 let 相关函数是 s7 的核心环境操作 API，此前虽然通过 `(scheme base)`
在 `(liii base)` 中可见，但并未正式 export，因此 `gf doc` 无法把它们识别为
`(liii base)` 的公开 API。正式 export 后，`gf doc funclet` 等命令才能工作，
这些函数也才成为 `(liii base)` 的稳定公开接口。

### How
- **export 顺序优先**：`gf doc --build-json` 扫的是 `*load-path*` 里各库的
  export 列表，必须先 export 才能被识别。所以先改 `base.scm`、再写测试、
  最后重建索引。
- **测试文件即文档**：每个测试文件开头用注释块写明语法 / 参数 / 返回值 / 说明，
  `gf doc` 直接展示测试文件内容作为文档。
- **语义探查**：s7 的环境语义有几处不直观，需先探查再写断言：
  - `(curlet)` 每次调用返回不同对象（不能假设 `eq?` 为 #t）
  - 顶层 `define` 的过程，其 `funclet` 包含参数槽（`(inlet 'x ())`），
    而非 rootlet；只有 C 内建函数的 funclet 才是 rootlet
  - `sublet` 创建新 let（不改父），`varlet`/`cutlet` 就地修改 target-let
    并返回同一对象
  - `unlet` 返回包含内建函数原始绑定的 let，典型用法是
    `(with-let (unlet) ...)` 以访问被遮蔽的原始版本

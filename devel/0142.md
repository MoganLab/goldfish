## 2026-09-08 os-call 统一抛出 type-error

### What

1. `src/liii_os.cpp` 的 `f_os_call` 改用 `string_type_error` 辅助函数抛出 `type-error` 代替 `wrong-type-arg`；Scheme 包装层 `os-call` 保持直接透传，由 C++ 层单一来源保证类型安全。
2. `tests/liii/os/os-call-test.scm` 的文档及测试断言统一改为 `type-error`。
3. 在 `CLAUDE.md` 明确规范：新增代码优先使用 `type-error` 而不是 `wrong-type-arg`。

### Why

`type-error` 符合 Goldfish Scheme 标准错误体系，比 s7 内置的 `wrong-type-arg` 更加规范、直观且容易记忆。由 C++ 底层统一做守卫可以同时保护 Scheme 包装层及直接调用 `g_os-call` 的场景，避免 Scheme 层出现冗余校验。

## 2026-09-08 C++ 层为 os-call 增加参数类型检查

### What

1. `src/liii_os.cpp` 的 `f_os_call` 入口处增加类型守卫：参数不是 string 时
   返回 `s7_wrong_type_arg_error(sc, "os-call", 1, cmd_arg, "a string")`。
2. `tests/liii/os/os-call-test.scm` 增加 5 个参数类型回归测试
   （integer/symbol/boolean/pair，以及 C 层入口 `g_os-call`）。
3. 修复前运行测试文件会直接段错误（SIGSEGV, exit 139），修复后 6/6 通过。
4. 崩溃片段 `demo/crash/h01-os-call-public-integer.scm`
   （`(import (liii os)) (os-call 42)`）修复验证完成后移除，
   修复后它不再段错误，而是输出
   `;os-call first argument, 42, is an integer but should be a string`（exit 255）。

### Why

`bin/gf demo/crash/h01-os-call-public-integer.scm`（即
`(import (liii os)) (os-call 42)`）会让进程段错误。根因在 C++ 层：
`f_os_call` 直接 `s7_string(s7_car(args))`，而 `s7_string` 底层是
`(T_Str(p))->object.string.svalue`（`s7_internal.h`，`T_Str(P) = P`），
对非字符串对象等同于把对象强转为字符串 cell 解引用，得到的垃圾指针
随后传入 `wordexp()` 触发段错误（gdb 栈顶为 libc `wordexp`）。

按讨论，该防御放在 C++ 层而非仅在 Scheme 包装层（`os.scm` 的
`os-call` 直接透传 `g_os-call`），这样根环境直接调用 `g_os-call`
的代码也受到保护。

### How

在 `f_os_call` 中先取 `s7_car(args)` 做 `s7_is_string` 检查，非字符串走
s7 标准的 `s7_wrong_type_arg_error`（与 `s7_liii_string.c` 现有风格一致），
抛出可被 `(catch 'wrong-type-arg ...)` 捕获的 Scheme 错误。

注意：同类的未检查入口（`f_rename`、`f_listdir`、`f_which`、
`g_bytevector-base64-encode` 长度参数等，见 `demo/crash/README.md`）

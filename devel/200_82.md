## 2026/8/24 定制 cpr/libcurl 构建配方

### What
1. 从 mogan 拷贝 `3rdparty/curl-8.21.0` 源码（约 14MB）进本仓库。
2. `xmake/packages/l/libcurl/xmake.lua` 整体替换为 mogan 版本：
   - `set_sourcedir` 指向仓库内 `3rdparty/curl-8.21.0`，不再从网络下载 8.11.1；
   - 不调用 `package:version()`（set_sourcedir 无版本号，调用会报 nil）；
   - macOS 走 OpenSSL（curl 8.21 已删除 SecureTransport），默认启用 openssl3
     （curl 8.21 起 `lib/vtls/openssl.c` 硬 #error 要求 OpenSSL >= 3.0）；
   - mingw 补 iphlpapi/secur32/bcrypt/normaliz 系统依赖；
   - 关闭 vendored 源码中已不存在的 docs/tests 相关目标；按包实例 hash 拆分 buildir。
3. `xmake/packages/c/cpr/xmake.lua` 按 mogan 定制：
   - 保留本地 `set_sourcedir(3rdparty/cpr)`（cpr 1.11.1）；
   - `on_load` 去掉 ssl 分支，统一依赖不带额外 configs 的 libcurl（不再引入
     `{libssh2=true, zlib=true}` 与 libssh2，避免第二个 libcurl 实例导致符号冲突）；
   - `on_install` 改为 `!wasm and !bsd`，清除 `-Werror`，MSVC 加 `/EHsc`。
4. `xmake.lua` 顶层增加：
   - `add_requires("libcurl", {system=false})`
   - `add_requires("cpr", {system=false, configs={ssl=true}})`（原为无选项的
     `add_requires("cpr")`）

### Why
- 顶层不 `system=false` 时，libcurl 会解析为系统包（apt 的动态 libcurl.so.4），
  与 cpr 链入的 openssl 混链，HTTPS 存在 ABI 不匹配段错误风险（mogan devel/2092.md）。
- cpr 默认 ssl=false 时 libcurl 无法发起 HTTPS 请求。
- mogan 已在 macOS/Linux/Windows CI 上验证过这套配方，直接移植可复用其修复
  （WebSocket ws_flush 忙转、LNK2019、openssl 版本等）。

### How
与 mogan 的差异仅两处：libcurl 的 `set_sourcedir` 用 `os.scriptdir()` 相对路径
（与 goldfish 现有 cpr 配方惯例一致，mogan 用 `os.projectdir()`）；cpr 保留本地
`set_sourcedir(3rdparty/cpr)` 而非 mogan 的版本号下载方式。

### 验证
- `ldd bin/gf` 不再出现动态 libcurl.so.4；
- 二进制内嵌 `8.21.0` 版本串；
- `tests/liii/http*` 全部 12 个测试文件通过（含 httpbin.org 真实 HTTPS 请求）。

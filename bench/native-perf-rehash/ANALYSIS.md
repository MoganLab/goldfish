## 集合规模的具体瓶颈

`Evaluator::vector_values` 按值返回整个 `std::vector<Value>`。
[vector-length](../../src/runtime/standard_primitives.cpp#L2885) 用复制结果求长度，
[vector-ref](../../src/runtime/standard_primitives.cpp#L2890) 用复制结果读取一个元素。
两种访问均随向量长度线性增长。

哈希表的插入会求桶数、读取桶；扩容会反复求旧桶数、读取新旧桶。
因此修复重复搬运后，这些访问仍会复制不断变宽的桶数组。对正常分布且按倍数
增长的桶数组，插入累计复制量可达平方增长；扩容的桶遍历也存在同类复制成本。
这是根据源码得出的复杂度结论，不能用少数时间样本证明整个集合的渐近复杂度。

固定执行 20,000 次访问，同一进程内改变向量宽度，所有校验通过：

| 向量长度 | vector-ref | vector-length |
|---:|---:|---:|
| 8 | 0.11191 秒 | 0.10871 秒 |
| 8,192 | 0.22633 秒 | 0.19594 秒 |
| 65,536 | 1.16665 秒 | 0.93339 秒 |

时间包含固定循环、求和与最终校验，见 [vector/vector.stdout](vector/vector.stdout)。
宽度 65,536 相比宽度 8，读取约慢 10.4 倍，求长度约慢 8.6 倍。

集合采样通过 FIFO 在 `profile-set` 阶段开始后启用，结束时关闭，排除了启动、
导入和输入列表生成。两种负载均插入总计 50,000 个元素，并校验每个集合的大小、
末元素存在及越界元素不存在：

| 负载 | 阶段时间 | 样本 | vector_values 调用路径占比 | memmove 自身占比 |
|---|---:|---:|---:|---:|
| 5 次构造 10,000 元素集合 | 8.12170 秒 | 799 | 13.27% | 7.76% |
| 1 次构造 50,000 元素集合 | 11.95513 秒 | 1,172 | 27.73% | 17.92% |

`vector_values` 一列是包含子调用的 CPU 占比；`memmove` 是自身占比，二者
不能相加。调用链明确连接了向量原语、`vector_values` 和内存复制。
负载、GC 状态和机器调度不同，两个时间不能当作严格 A/B 性能比值；宽向量
探针与源码说明访问本身的缺陷，采样说明它确实发生在集合构造热路径。

第一项优化应让读取元素和求长度直接访问已检查类型的向量存储，保留错误、
边界和修改后的可见性。序列化等确实需要快照的调用继续显式复制。验证后先
重跑宽向量探针、集合阶段 perf 和此前受限的 100,000 档，再判断是否升级。

## 启动成本

最小表达式 `(+ 1 1)` 的热缓存启动，现有诊断计时如下：

| 阶段 | 耗时 |
|---|---:|
| kernel 加载 | 0.060 秒 |
| 缓存 runtime 加载 | 0.348 秒 |
| install.scm 源码加载 | 2.442 秒 |
| native Scheme surface 源码加载 | 3.380 秒 |
| standard-library 恢复 | 0.647 秒 |
| 模式导入、reader、writer 及之前的 collect | 10.937 秒 |
| 整体启动 | 17.825 秒 |

最后一个诊断标签叫 `load-source-reader`，但它的时间区间还包含
`collect()`、`install_mode_imports()` 和 `native-write.scm`，不能把全部
10.937 秒归于 reader。其他阶段之间也包含现有计时边界内的操作。
真正的缓存 runtime 加载很快；慢的是缓存加载之后的启动工作。

启动 perf 的自身 CPU 热点包括解释器主循环 12.31%、`GC_free` 11.86%、
`GC_mark_from` 8.49%、环境查找 8.15%、`GC_malloc` 4.79%。其中
`load-source-reader` 区间约占启动墙钟时间 61%，但这不是该阶段的独立采样占比。

第二项优化应先细分这个启动区间，再评估由原生编译器生成并缓存 reader、
writer 等引导源码的展开结果，保留无缓存源码引导路径及版本失效机制。
需要核对它们的动态安装行为，不能直接把现有 `load-source-file` 换成普通
库导入或缓存恢复。当前证据不支持优先优化缓存文件读取。

   仓库要求运行 changed-since 门禁，再做同输入 perf 和有截止时间的规模复测。

   分别比较各启动阶段时间，不能只比较总耗时。
3. 再处理解释器容器分配与查找：当前集合样本中 continuation 帧及 Value 向量
   分配、复制、销毁和 GC 明显。先减少短命容器及重复查找，再决定是否需要
   注册集合插入的原生热路径，并检查编译器内联后的真实调用点。

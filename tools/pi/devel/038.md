## 背景与取证

1. **首次发现（029 验收执行器，2026-10-19）**：
   `tools/pi/devel/029.scm` 在工作区初始版本中未显式导入 `(scheme process-context)`，
   仅导入 `(liii pi)` 后调用 `get-environment-variable`，进程直接段错误退出；
   补上 `(scheme process-context)` 后脚本恢复正常。该修复与其注释保留在
   commit `a5ff91b3` 的 `029.scm` 中：
   “若不显式导入会解析到 define-library 泄漏的破损绑定并段错误（goldfish 内核 bug）”。
2. **同类先例（027 验收，2026-10-19）**：
   `string-prefix?` 未被 `(liii string)` 导出，未显式导入 `(srfi srfi-13)` 时
   同样解析到 define-library 泄漏的破损绑定并段错误；
   见 `tools/pi/devel/027.md` 的执行与验收记录。说明这不是单个函数的偶发问题，
   而是库加载/绑定复制层的一类缺陷。
3. **现状是“被显式导入掩盖”**：当前所有会用到 `get-environment-variable` /
   `process-spawn` 的测试与验收脚本都显式导入了对应库
   （`(scheme process-context)` / `(liii subprocess)`），因此基线测试全绿，
   缺陷不可见。开发阶段必须补一个**故意不显式导入**的最小复现测试。
4. **附加线索：process-spawn 直跑段错误**：用户提供线索，直接运行使用
   `process-spawn` 的脚本也可触发段错误；开发阶段需复现并判断是否与
   `get-environment-variable` 同根因（同为“未显式导入 → 破损绑定”），
   同根因则合并修复，不同根因则登记独立任务。
5. **基线对照（文档阶段已跑，均通过）**：
   - `bin/gf tests/scheme/process-context/get-environment-variable-test.scm`：4/4
   - `bin/gf tests/scheme/process-context-test.scm`：通过
   - `bin/gf tests/liii/subprocess/process-spawn-test.scm`：17/17
   三者均显式导入了对应库，因此只能证明显式导入路径正常，不能证明泄漏路径正常。

## 初步根因假设（开发阶段验证，不作为结论）

- 假设 A：**import 后符号 local-slot 缓存悬垂**。`g_import` 通过
  `s7_let_to_list` + `s7_varlet` 把库导出的值复制到导入方环境；
  `s7_varlet` 会更新符号的 local-slot 缓存。若某个中间环境
  （如 `r7rs_import_only/prefix/rename` 创建的临时 inlet，或未登记的
  lib_env）在 import 完成后被 GC，而符号缓存仍指向其中的 slot，
  之后对同一符号的查找就会读到已释放内存并段错误。
- 假设 B：**库体定义泄漏到 rootlet 半失效 slot**。`g_define_library` 在
  `s7_rootlet` 上注册库名兼容符号，并在子环境求值库体；若某些路径把
  `get-environment-variable` 的 global slot 指向了随后失效的 local slot，
  顶层直接调用即崩溃。
- 假设 C：非泄漏问题，而是 `f_get_environment_variable` 在特定参数/环境下
  的裸 longjmp / RAII 路径问题；但 029 的“加显式导入即恢复”证据不支持此假设，
  仍需在修复前用 gdb backtrace / ASAN 排除。

开发阶段要求：先用最小复现测试固定失败现象，再用 gdb（必要时 ASAN 构建）
拿到 backtrace，确认 A/B/C 中哪一个成立，再决定修复点；**不允许在未定位根因时
用 try/catch 或包装函数掩盖段错误**。

## 验收点

1. **根因定位**：给出可复现的最小 Scheme 片段与崩溃 backtrace（或等价证据），
   明确根因属于 import/define-library 绑定层还是 C 函数本身。
2. **修复或受控约束**：优先在内核层修复，使
   `(import (liii pi))` 后未显式导入 `(scheme process-context)` 时调用
   `get-environment-variable` **不再段错误**；语义二选一且必须明确：
   返回正确环境变量值，或抛出结构化 `unbound-variable` 错误；
   不允许返回错误值或静默成功。若最终选择“文档化导入约束”而非修复，
   必须先经用户确认，并在 `PI_SPEC.md` 写明约束。
3. **同类场景验证**：验证 `(srfi srfi-13)` 的 `string-prefix?` 泄漏是否同根因；
   验证 process-spawn 直跑段错误线索并归类（同根因合并修复，否则登记新任务）。
4. **TDD 最小复现**：新增 `tools/pi/tests/liii/pi-import-leak-test.scm`，
   内容仅 `(import (liii check) (liii pi))` 后直接调用
   `(get-environment-variable "PATH")` / 不存在的键；修复前该测试稳定崩溃
   （非 0 退出），修复后通过。若修复涉及内核，同时在 `tests/scheme/` 下补
   对应的内核级防回归测试。
5. **无回归**：`(scheme process-context)`、`(liii subprocess)`、`(liii pi)`
   既有测试全部通过；显式导入路径行为不变。
6. **门禁**：`xmake b goldfish`、`bin/gf fmt`、`git diff --exit-code`、
   `bin/gf check` 全过；新增测试文件后执行 `bin/gf doc --build-json`。

## 2026-10-20 任务描述

### What

1. 阅读 `PI_PLAN.md` §3 任务 038 的验收点与历史线索
   （029 验收执行器、027 的 `(srfi srfi-13)` 同类记录、process-spawn 直跑线索）；
2. 从 `tools/pi/devel/ddd.md` 模板建立本任务文档，登记状态、涉及文件、
   验收点、测试方法、初步根因假设；
3. 跑通三条显式导入路径的基线测试，确认现有测试因显式导入而无法暴露缺陷；
4. 开发阶段将按 TDD 先补最小复现测试，再用 gdb/ASAN 定位根因并修复。

### Why

`(liii pi)` 内部有 8 个库消费 `get-environment-variable`，而门面本身不导出它。
一旦 import 绑定层留下悬垂绑定，任何未显式导入 `(scheme process-context)`
的脚本（包括验收脚本、用户脚本）都会在调用时直接段错误，无法给出可诊断错误。
该缺陷与 `(srfi srfi-13)` 泄漏同类，属于内核级绑定生命周期问题，
必须先定位根因，避免后续任务继续以“多写一行 import”绕过。

### How

1. 最小复现：新建只导入 `(liii check)` 与 `(liii pi)` 的测试文件，直接调用
   `get-environment-variable`，记录退出码与崩溃栈；
2. 根因验证：阅读 `src/s7_r7rs_library.c` 的 `g_import` / `r7rs_import_*`
   与 `src/s7_scheme_let.c` 的 `s7_varlet`，用 gdb watch/bt 确认是临时环境
   GC 后 local-slot 缓存悬垂，还是 global slot 指向失效 let；
3. 修复策略：在符号 local-slot 缓存失效或 import 临时环境保活处修复；
   修复后同时验证 `string-prefix?` 与 process-spawn 线索；
4. 防回归：最小复现测试 + 既有显式导入测试双跑，确保“泄漏路径不崩、
   显式路径行为不变”。

## 验收脚本（REVIEW 阶段产物 038.scm 的写法）

- Scheme 脚本，`bin/gf tools/pi/devel/038.scm` 直接运行。
- 外部命令一律用 `(liii subprocess)` 的 `run` 执行，**必带 `:timeout`**；
  每步用 `(liii check)` 断言退出码与关键输出。
- 段错误不能用 `(liii check)` 直接断言，须 `run` 子进程 `bin/gf test ...`
  并断言退出码与 stderr 摘要；修复前记录非 0 退出作为失败证据，
  修复后断言 0 退出且输出符合预期。

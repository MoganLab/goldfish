## 验收点

1. **multikey.json 配置读取**：
   - 复用 `~/.pi/agent/multikey.json`（受 `PI_CODING_AGENT_DIR` 重定向），存在与所选
     provider 对应的 pool 时读取 `keys` 列表并过滤 `enabled: false` 的 key；
   - 无对应 pool（或文件不存在）时回退既有 `auth.json` 路径，行为与现状完全一致；
   - pool 附带 `cooldownMs`（默认 20000）/`invalidKeyCooldownMs`（默认 600000）可配置。
2. **cooldown + LRU 轮换状态机**：
   - 内存状态机记录各 key 的 cooldown-until 与最近使用时间（LRU）；
   - 请求遇 HTTP 429 冷却当前 key（默认 20s 或 `cooldownMs`），遇 403/invalid key
     冷却（默认 600s 或 `invalidKeyCooldownMs`）；
   - **未输出实质内容前**（首字节/首个增量事件之前）透明切换下一可用 key 重试；
     已开始输出后失败按既有重试/报错路径，不做半截切换；
   - pool 全部 key 冷却/耗尽时才结构化报错（退出码 1）。
3. **日志安全（脱敏）**：
   - 任何日志/错误摘要中 key 仅打印前后若干字符（如 `sk-kim...8ByO`），
     完整 key 不出现在 stdout/stderr/会话文件的错误条目中（遵守 PI_PLAN §2 日志安全）。
4. **TDD 覆盖**：
   - 解析/选取/冷却算法单测（fixture 驱动）；
   - key1 403 自动轮换 key2 成功的**非流式**与**流式（SSE）**用例各一（stub server）；
   - 无 pool 回退 auth.json 的兼容用例；
   - pool 全耗尽报错用例。

3. 明确预估代码文件、验收点与测试方法（见上）。

#### Why

- 单一 API key 在 429（限流）/403（失效）场景下只能按固定重试等待，成功率低；
  多 key pool + 自动轮换可在未输出实质内容前透明换 key，显著提升脚本模式
  在非交互批处理下的成功率。
- 对照 Node pi 的 `pi-multikey` 扩展形态，bin/gf pi 原生实现，复用同一份
  `multikey.json` 配置（只读，绝不写入 `~/.pi/agent/`）。

#### How

- **解析层**：新增 `(liii pi multikey)`，`pi-load-multikey` 读
  `<agent-dir>/multikey.json`（`PI_CODING_AGENT_DIR` 重定向），返回按 provider id
  索引的 pool alist；过滤 `enabled: false` 的 key；冷却时长取 pool 配置否则默认
  （429→20s，403/invalid→600s）。
- **状态机**：pool 运行时状态（各 key cooldown-until、last-used）存内存 record/
  关联表，随进程生命周期；选取 = 过滤冷却中 key 后取 LRU。
- **接入点**：`pi-resolve-provider-key` 有 pool 时返回「当前选中 key」；provider
  请求层捕获 429/403 响应，若尚未输出实质内容（首字节前）则
  `pi-multikey-mark-cooldown` 冷却当前 key 并换 key 重发（计入重试上限防死循环）；
  pool 耗尽抛结构化错误。流式与非流式共用同一判定（以是否已 emit
  message_update/写 stdout 为界）。
- **脱敏**：错误/日志中 key 一律 `%mask-key`（前 6 + `...` + 后 4）。
- **TDD**：fixture `tools/pi/tests/fixtures/multikey/multikey.json` 自建；
  e2e stub server 首个请求对 key1 回 403/429、对 key2 回正常响应，
  断言最终成功且请求顺序正确（非流式 + SSE 各一）。

### 命令面（实测四种形态）

Scope 行为实测，收集命令据扩展源码判定（★）：

| 形态 | 收集方式 | 实测 Scope 行 |
|---|---|---|
| `/simplify` | ★ `git diff --name-status HEAD`（含暂存 + 未暂存）；主命令失败或为空时回退 `git diff --name-status HEAD~1` | `- src/calc.ts (modified; changed lines: 21-33)` |
| `/simplify --staged` | ★ `git diff --name-status --cached` | `- src/util.ts (added; entire file is in scope)` |
| `/simplify --ref=main` | ★ `git diff --name-status main` | `- src/calc.ts (modified; changed lines: 21-30)` 与 `- src/util.ts (added; entire file is in scope)` |
| `/simplify src/calc.ts` | ★ 指定文件视为 `modified`，行范围由 `git diff --unified=0 --no-ext-diff HEAD -- <path>` 得出 | `- src/calc.ts (modified; changed lines: 21-30)` |

补充细节（★ 为源码判定，其余为实测）：

- ★ **收集命令**：`git diff --name-status [HEAD|--cached|<ref>]`，
  主命令失败或结果为空时回退 `git diff --name-status HEAD~1`；
  显式给出文件时按 `modified` 处理，行范围由
  `git diff --unified=0 --no-ext-diff <ref> -- <path>` 得出。
- ★ **行范围算法**：解析 `git diff --unified=0` 的 hunk 头 `@@ -a,b +c,d @@`，
  取新文件侧起始行 `c` 与行数 `d`（`d=0` 视为纯删除、跳过），相邻 hunk 合并为
  连续区间；新增文件（状态 `A`）整文件在范围内；重命名/复制取新路径。
- **无改动**：通知 `No changed files found. Specify file paths or make some changes
  first.`（rpc 事件 `extension_ui_request` / `notify` / `info`），
  **不启动 agent 回合**（事件序列只有 `extension_ui_request` + `response`）。
- ★ **降级措辞**：diff 失败时 Scope 行写 `(modified; changed lines unavailable —
  inspect git diff before editing)`；改动行集合为空时写
  `(modified; deletions only — no current lines to simplify)`。
- ★ **`--staged` 与回退**：暂存区为空时回退逻辑仍走 `HEAD~1`（不区分 `--staged`），
  即暂存区无改动时可能审查到上一提交的差异。

### 提示词（实测原文结构）

固定四原则（Preserve functionality / Apply project standards / Enhance clarity /
Maintain balance）+ `## Scope`（文件与改动行号列表，新增文件标注整文件在范围）+
`## Process` 5 步（读文件 → 找具体改进点 → 逐文件改且不越界 → 跑测试验证 →
总结）+ 禁止项（不加特性、不改公共 API、不越出行范围；越界的改进只写进总结）。

### 执行行为（实测）

agent 拥有完整工具（`bash` / `read` / `edit`）：先 `ls` / `git status` / `read` /
`git diff` / `git log` 探查，再 `edit` 改写**改动行范围内**的代码，随后跑
`tsc --noEmit` 等验证命令，最后输出总结。实测把 `computeTotalWithDiscount` 的
`let t` 改名为 `total`、`t = t + item` 改为 `total += item`、删除
`if (t > 100) { t = t * 1.0; }` 死代码；不在范围内的 `computeTotal` 中的同类问题
只写进总结、不改文件。

## 形态裁定

脚本模式无 TUI、无斜杠命令，映射为 CLI 开关，语义与原生 `/simplify` 对齐：

```bash
# 只读建议报告（默认）：不修改工作树
bin/gf pi --simplify
bin/gf pi --simplify --staged
bin/gf pi --simplify --ref=main
bin/gf pi --simplify src/foo.ts src/bar.py

# 应用模式：对齐原生，允许在改动行范围内改写文件并验证
bin/gf pi --simplify --apply
```

关键裁定点：

1. **默认只读，`--apply` 才写文件**。原生 `/simplify` 直接改写用户工作树；脚本模式
   一次性、无交互确认，默认写文件风险过高，故默认只产出建议报告，与 044 偏差 #12
   （审查只读）保持一致。`--apply` 提供原生对等能力。
2. **范围口径与原生一致**：以 `git diff --unified=0` 的改动行号为审查范围，
   新增文件整文件在范围内；越界机会只报告、不修改。
3. **只读模式用结构化输出契约**（与 044 同款）：要求模型返回 JSON 建议列表，
   解析容忍 ```json 围栏与前后说明文字；不可解析时降级为一条 `parse-error` 建议
   并继续输出报告，不抛未捕获异常。应用模式沿用原生自由文本总结（agent 自行总结），
   额外要求其在总结中单列越界机会。
4. **只读模式不给 agent 工具**（`:tools '()`，同 044 审查流程）：把改动行及其上下文
   内联进提示词，避免模型乱跑；应用模式使用标准工具集（read/bash/edit/write），
   范围约束靠提示词（与原生一致）。
5. **`--staged` / `--ref` 复用既有开关**：放宽其依赖校验，从「requires --code-review」
   改为「requires --code-review or --simplify」；`--apply` 单独出现时报可读错误。
6. **空场景**：无改动文件时输出 `No changed files found. Specify file paths or make
   some changes first.` 并以退出码 0 结束（与 044 一致）。

## 验收点

1. **CLI 形态与参数解析**：
   - `bin/gf pi --simplify` 审查未提交改动；`--staged` 只审查暂存区；
     `--ref=REF` 与指定 ref 比较；位置参数为指定文件列表（与原生 `/simplify` 对齐）；
   - `--apply` 单独出现（无 `--simplify`）报可读错误并退出码 1；
   - `--staged` / `--ref` 与 `--simplify` 组合合法，与 `--code-review` 组合仍合法；
   - 未知选项进入既有 unknown-flags 处理，不静默吞掉。
2. **变更文件与行范围收集**：
   - 复用 044 的 `pi-collect-changed-files`（`git diff --name-status`，必带 `:timeout`），
     默认 ref `HEAD`，失败/为空回退 `HEAD~1`，超过 10 个文件按上限截断并提示；
   - 逐文件执行 `git diff --unified=0` 解析 hunk 头得到改动行区间，
     相邻区间合并，纯删除（行数 0）跳过；
   - 新增文件（状态 `A`）整文件在范围内；diff 失败时降级为「行范围不可用」提示。
3. **Scope 描述构造**：
   - 逐文件生成 `- <path> (modified; changed lines: 21-33)` /
     `- <path> (added; entire file is in scope)` 形式的行；
   - 行范围为空时给出「无可简化行」的措辞；diff 失败时给出「行范围不可用」的措辞。
4. **提示词构造**：
   - 含四原则（保持功能 / 遵循项目规范 / 增强清晰度 / 保持平衡）、Scope 段、
     Process 段与禁止项（不加特性、不改公共 API、不越界）；
   - 只读模式含 JSON 结构化输出契约与「无建议时返回空数组」的约定；
   - 应用模式含「逐文件改、跑测试验证、总结并单列越界机会」的要求。
5. **只读建议流程与解析**：
   - 走既有 agent 循环（当前 provider、既有超时/重试/会话规范），工具集为空；
   - 解析 JSON 建议列表，容忍 ```json 围栏与前后说明文字；
     非法条目丢弃；整体不可解析时降级为一条 `parse-error` 建议，不抛未捕获异常；
   - **不修改工作树**（被审查文件前后哈希一致）。
6. **应用流程（`--apply`）**：
   - 使用标准工具集（read/bash/edit/write），提示词约束改动范围；
   - 输出 agent 的总结文本（Markdown），其中包含改动摘要与越界机会；
   - 真实冒烟能观察到文件被简化（改动落在改动行范围内）。
7. **报告输出**：
   - print 模式 stdout 打印 Markdown 建议报告：标题含建议条数、条目按文件与行号排列、
     每条含分类、`file:line`、说明与 `  Suggestion: ...`；
   - 无建议时输出 `No simplification opportunities found. Code looks clean.`；
   - JSON 模式输出对应事件且不破坏既有事件序列。
8. **边界与安全**：
   - 只读模式零写入；无凭据/超时/网络失败按既有错误规范报错并退出码 1；
   - 日志不泄露 API key、代理地址与请求体；
   - 所有外部命令与网络 IO 均带超时。
9. **回归与门禁**：
   - `bin/gf pi` 既有测试全绿；新增单元测试镜像源码库结构（一个函数一个测试文件）；
   - `xmake b goldfish` → `bin/gf fmt` → `git diff --exit-code` → `bin/gf check`
     → `bin/gf doc --build-json` 依次通过；单文件不超过 300 行。

### Why

任务 044-049 是一组「原生 pi 扩展 → `bin/gf pi` 脚本模式对应能力」的任务，
用户裁定必须先有原生 pi 的可运行对照基准，再实现脚本模式对应形态。
simplify 与 044 的 code-review 共享「git 变更收集 + 提示词构造 + 报告输出」
三块基础设施，但关注点不同：code-review 找**缺陷**（严重级分类），simplify 找
**可简化点**（清晰度/一致性/可维护性）且范围严格限定在改动行——这正是 044
未覆盖的能力面。

### How

1. **变更收集**：直接复用 044 的 `pi-collect-changed-files`（`git diff --name-status`
   + `HEAD~1` 回退 + 10 文件上限），不重复实现；
2. **行范围**：`pi-parse-changed-ranges` 解析 `git diff --unified=0` 的 hunk 头
   `@@ -a,b +c,d @@`，取新侧起始行与行数，跳过 `d=0`，合并相邻区间；
3. **Scope 描述**：`pi-build-scope-lines` 按原生措辞生成 Scope 行（modified/added/
   行范围不可用/无可简化行四种形态）；
4. **提示词**：按原生 `buildSimplifyPrompt` 的四原则 + Scope + Process 结构组织，
   只读模式追加 JSON 契约并内联改动行上下文，应用模式保留自由文本总结要求；
5. **解析与格式化**：JSON 解析 + 围栏剥离 + 逐条字段校验，失败降级为
   `parse-error`；格式化输出 `## Simplify Suggestions (N)` 与越界机会小节；
6. **接线**：`args.scm` 解析 `--simplify` / `--apply` → `modes/simplify.scm` 分派
   只读/应用两条流程 → print/JSON 两种输出；
7. **TDD**：先写单元测试（镜像源码结构、一个函数一个测试文件），再实现；
   验收脚本 `tools/pi/devel/045.scm` 逐条断言上述 9 组验收点。

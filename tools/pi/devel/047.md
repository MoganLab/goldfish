### 命令面（实测六条）

| 原生命令 | 行为 | 实测 |
|---|---|---|
| `/blueprint <objective>` | 把「资深架构师」计划生成提示词作为 follow-up 用户消息发给会话；模型探查代码库后调用 `blueprint_create` 落地计划 | ✓（提示词原文与工具入参均取到） |

| `/plan-verify` | 跑当前阶段的验证门；自动门全过则推进阶段 | ✓ |

`blueprint_status`（读进度）、`blueprint_update`（回写任务状态）、
`blueprint_next`（取下一个可执行任务）。

### 计划生成（实测：目标「Add OAuth2 login to the user service」）

模型先探查代码库（`ls -la` / `find` / `read` × 4 / `pytest` / `mypy --version`），
再调 `blueprint_create` 落地 **4 阶段 / 11 任务**：

```
Phase 1: User Identity & OAuth Storage Models        1.1 1.2 1.3   gates: tests_pass
Phase 2: OAuth2 Client & Provider Integration Layer   2.1 2.2 2.3   gates: tests_pass, typecheck_clean
Phase 3: OAuth2 Authentication Flow & Token Issuance  3.1 3.2 3.3   gates: tests_pass, typecheck_clean
Phase 4: End-to-End Integration & Documentation       4.1 4.2        gates: tests_pass, typecheck_clean, user_approval
```

任务 ID 形如 `phase.task`（`1.1` / `2.3`）；每个任务含 title / description /
acceptance_criteria（可测条件，2-3 条）/ file_targets（真实路径）/ dependencies（任务 ID）。
模型产出的计划在**结构与约束**上稳定对齐 native 提示词的要求（2-6 阶段、每阶段 2-8 任务、
ID 形如 `phase.task`、依赖最小且无环、验收标准可测、文件目标指向真实路径）。

### 数据模型（实测 `state.json`）

- **blueprint**：`id`（`bp-<base36 时间戳>`）、`objective`、`project_id`、`status`
  （draft/active/completed/abandoned）、`created_at`、`updated_at`、`phases`、
  `active_phase_id`、`active_task_id`。
- **phase**：`id`、`title`、`description`、`status`（pending/active/completed/verified）、
  `tasks`、`verification_gates`、`started_at`、`completed_at`。
- **task**：`id`、`title`、`description`、`status`（pending/in_progress/completed/blocked/skipped）、
  `acceptance_criteria`、`file_targets`、`dependencies`、`started_at`、`completed_at`、
  `session_id`、`notes`。
- **verification_gate**：`type`（tests_pass / typecheck_clean / user_approval / custom_command）、
  `command`、`description`、`passed`、`last_checked_at`、`error_message`。

### 依赖跟踪（实测）

- 创建即重算阻塞：`1.1`（无依赖）→ `pending`；`1.2`（依赖 1.1）、`1.3`（依赖 1.2）→
  `blocked`；`2.1`/`3.1`（无依赖）→ `pending`；跨阶段依赖同样生效
  （`3.2` 依赖 `1.3, 2.3, 3.1` → `blocked`）。
- 完成 `1.1` 后自动解阻：`1.2` 由 `blocked` 回到 `pending`，`active_task_id` 前移到 `1.2`。
- 环检测：`blueprint_create` 传入 `1.1 → 1.2 → 1.1` 时被拒，工具返回
  `Error: Dependency cycles detected: [["1.1","1.2"]]`，**不落盘**。

### 验证门（实测）

- `custom_command` 门（`python3 -m pytest -q`）→ `PASSED (243ms)` → 阶段推进为
  `verified` → 单一阶段时整个 blueprint 置 `completed`（`active_phase_id`/`active_task_id`
  清空）。
- 门禁结果落盘：`passed=true`、`last_checked_at` 有值、失败时 `error_message` 存命令输出。
- 审计流水（`history.jsonl`）逐条追加：`blueprint_created` / `task_started` /
  `task_completed` / `verification_passed` / `verification_failed` / `blueprint_abandoned`。

### 多会话持久化与上下文注入（实测）

新建蓝图后**另起一个 pi 进程**（同一 cwd）：

- `session_start` 时从 `~/.pi/blueprints/index.json` 的 `active_blueprint_id` 载入状态；
- `before_agent_start` 把 blueprint 上下文块追加到系统提示词末尾。实测模型在**不调用
  任何工具**的前提下逐字复述出了注入内容：

```
## Active Blueprint: "Session persistence probe"

### Current Phase: Phase 1 - Persistence phase
Status: pending | 0/1 tasks completed

### Current Task: 1.1 - Persisted task
the description of the persisted task

**Acceptance criteria:**
- crit one

**File targets:**
- src/token_service.py

### Phase 1 Verification Gates
- [ ] Run pytest
```

即**计划跨进程存活 + 每回合自动注入**，这是 native 的招牌能力。

### 实测缺陷（四条，均有源码依据）

1. **print 模式空输出**：`pi -p "/blueprint ..."` 退出码 0、**stdout 0 字节**。扩展用
   `pi.sendUserMessage(..., {deliverAs: "followUp"})` 派发任务（★ `blueprint-command.ts` /
   `plan-next-command.ts`），print 模式不等待异步 follow-up 回合（与 044 偏差 #15、
   045 偏差 #17、046 偏差 #21 同源）。
2. **内置门禁类型写死 Node 工具链**：`tests_pass` → `npm test`、`typecheck_clean` →
   `npx tsc --noEmit`（★ `verification.ts` 的 `resolveCommand`）。在 Python 工程里跑
   `tests_pass` 门必然失败，实测错误信息为
   `npm error code ENOENT ... Could not read package.json`（91ms 即失败）。
   **非 Node 工程只有 `custom_command` 门可用**。
3. **`user_approval` 门禁死锁**：★ `plan-verify-command.ts` 对 `user_approval` 门
   **从不调用** `verifyGate`（直接 `continue`），因此 `passed` 永远为 `false`；而
   ★ `state-machine.ts` 的 `advancePhase` 要求**所有**门 `passed` 才推进阶段 →
   阶段永远无法 `verified`，blueprint 永远无法 `completed`。实测：连跑两次
   `/plan-verify` 均输出「Automated gates passed. User approval still required.」，
   阶段卡在 `completed`（任务全完成）但门禁 `passed=false`。扩展**没有提供任何
   放行人工门的入口**。
4. **门禁超时写死且同步阻塞**：★ `verification.ts` 的 `runGate` 用
   `execSync(command, {timeout: 120_000})`——超时不可配置，且同步阻塞事件循环。

### 其他实测观察（非缺陷但影响移植取舍）

- **门禁 `type` 不做校验**：★ `blueprint-tools.ts` 的 `buildPhases` 直接透传 `rg.type`，
  传入非法类型（如 `"test"`）被静默接受——schema 约束只在 LLM 侧。
- **`project_id` 恒为 `"unknown"`**：★ `state.project` 从未被赋值，`project_id` 取
  `state.project?.id ?? "unknown"`。即 native 的蓝图**并不按项目隔离**。
- **`session_id` 恒为 `""`**：★ 扩展的 `state.sessionId` 初始化为空串且无处赋值，
  `history.jsonl` 每条记录的 `session_id` 都是 `""`。
- **同一时刻只允许一个活动蓝图**：★ `blueprint-command.ts` 与 `blueprint_create`
  都检查 `status === "active"`，冲突时给通知：
  `An active blueprint already exists: "..."` / `Use /blueprint abandon to discard it, or /plan-status for details.`
- **无蓝图时三条命令统一提示** `No active blueprint.`（实测 `/plan-status` /
  `/plan-verify` / `/plan-next` 三者一致）。
- **无可执行任务时的提示**：`No actionable tasks. Some may be blocked or awaiting verification.`
  （蓝图 `completed` 时则是 `Blueprint is complete.`）。
- **`/plan-verify` 无活动阶段**：提示 `No active phase to verify.`。
- **门禁在工程根目录执行**：★ `runGate(gate, cwd)`，`cwd` 取 `state.project?.root ?? process.cwd()`。

## 形态裁定

脚本模式无 TUI、无斜杠命令、无 `~/.pi/blueprints/` 共享目录，但 blueprint 的**核心价值
恰恰是跨会话的多会话计划**——因此不能照搬 045/046 的「零外部状态」约定。
裁定如下。

### 1. 命令面：4 个斜杠命令 → 5 个 CLI 开关

```bash
# 生成计划（等价 /blueprint <objective>）
bin/gf pi --blueprint "为用户服务加入 OAuth2 登录"

# 打印进度与计划（等价 /plan-status）
bin/gf pi --plan-status

# 取出下一个可执行任务并驱动一次实现（等价 /plan-next）
bin/gf pi --plan-next

# 跑当前阶段的验证门（等价 /plan-verify）
bin/gf pi --plan-verify

# 放弃当前计划（等价 /blueprint abandon）
bin/gf pi --plan-abandon
```

互斥与前置（`args.scm` 校验，报可读错误并退出码 1）：

- `--blueprint` / `--plan-status` / `--plan-next` / `--plan-verify` / `--plan-abandon`
  五者互斥（一次调用只做一件事）；
- `--blueprint` / `--plan-next` 与 `--code-review` / `--simplify` / `--red-green` 互斥
  （同一轮只能有一种工作流；对齐 046 已有的互斥校验风格）；
- `--approve` 只允许与 `--plan-verify` 同用（用于放行人工门，见 §4）；
- `--blueprint` 缺目标描述（无消息、无 `@file`）时报可读错误并退出码 1
  （对齐 046 的 `--red-green` 校验）；
- `--plan-status` / `--plan-next` / `--plan-verify` / `--plan-abandon` 在没有活动计划时
  打印 `No active blueprint.` 并以退出码 0 结束（对齐 native 的提示语义；
  「无计划」不是错误）。

### 2. 状态落盘：项目本地 `.pi/`，不写 `~/.pi/`

- 机器可读状态：`.pi/blueprint.json`（唯一真相源，对齐 native 的 `state.json`）；
- 人读计划：`.pi/blueprint.md`（对齐 native 的 `plan.md`，每次保存重新渲染）；
- 审计流水：`.pi/blueprint.history.jsonl`（对齐 native 的 `history.jsonl`）；
- 路径可用 `--blueprint-file <path>` 覆盖（便于测试用临时目录）。

裁定理由：

1. **多会话是本功能的立身之本**，纯进程内状态（045/046 的做法）会直接废掉该特性；
2. **不写 `~/.pi/blueprints/`**：那是原生 pi 的数据目录，`bin/gf pi` 与原生 pi 在同一台
   机器上共存时互相污染会引发难以排查的状态错乱；本项目对 `~/.pi/agent/` 一直保持
   只读复用的约定，不应例外；
3. **项目本地天然按 cwd 隔离**——native 的 `project_id` 恒为 `"unknown"`（并不按项目隔离），
   本项目按 cwd 精确隔离是**改进**而非对齐；
4. 计划文件在工程内可见、可 diff、可随仓库共享，契合「与现有三阶段流程互补」的定位
   （计划即工程内的一等产物）。

### 3. 计划生成：模型出结构化 JSON，Scheme 侧确定性落地

native 靠 LLM 工具 `blueprint_create` 落地计划（模型直接写盘）。脚本模式改为：

1. 用主模型按 native 提示词结构（★ `prompts/blueprint-generate.ts` 原文改写为 Scheme
   字符串常量）产出**结构化 JSON 计划**：`{objective, phases:[{id,title,description,
   tasks:[{id,title,description,acceptance_criteria,file_targets,dependencies}],
   verification_gates:[{type,description,command}]}]}`；
2. Scheme 侧解析并**确定性校验**：任务 ID 唯一、依赖指向存在的任务、**环检测**、
   阶段/任务数量上下界、门禁类型合法性（对齐 native 提示词的 2-6 阶段 / 2-8 任务约束）；
3. 校验通过才落盘 `.pi/blueprint.json` + `.pi/blueprint.md`；失败则打印可读错误
   （含失败原因摘要）并退出码 1。

这样做的收益：环检测与依赖校验从「模型自觉」变成「确定性代码」，可单元测试；
也不新增「让模型调用写盘工具」的攻击面。

**不提供 `blueprint_create` 工具**（对齐 native 的四工具集但砍掉一个）：
计划落地只由 `--blueprint` 流程完成，模型在实现回合不得改写计划（防止实现过程中
悄悄重规划）。这是有意偏差（见 §6）。

### 4. 验证门：修 native 的两个门禁缺陷

- 门禁类型只保留 **`custom_command`**（主）与 **`user_approval`**（人工确认）。
- **不提供** `tests_pass` / `typecheck_clean`：native 把它们写死成 `npm test` /
  `npx tsc --noEmit`，在非 Node 工程必然失败（实测缺陷 2）。若计划里出现这两个类型，
  报可读错误「门禁类型 `tests_pass` 在脚本模式下不可用，请改用 `custom_command`」，
  **绝不静默改跑 npm**。
- **`user_approval` 死锁修复**：native 的人工门永远 `passed=false`，阶段永远无法推进
  （实测缺陷 3）。脚本模式提供 `--approve` 显式放行：
  `bin/gf pi --plan-verify --approve` 把当前阶段的人工门标记为通过；未带 `--approve`
  时行为与 native 一致（报告「仍需人工确认」且不推进阶段），但**存在明确出口**，
  不构成死锁。
- 门禁命令用 `(liii subprocess)` 的 `run` 执行，**必带 `:timeout`**（默认取 `--timeout`，
  120s）——修 native 写死 120s 不可配的问题（实测缺陷 4），同时满足 PI_PLAN §2
  「每一条命令、每一次 IO 都必须有超时」的强制规范。
- 门禁在**当前工作目录**执行（对齐 native 的 `process.cwd()` 语义）。
- 门禁失败不抛未捕获异常：记录 `passed=false` + 错误摘要到状态与 history，
  命令行报告失败并以退出码 1 结束。

### 5. 内置工具与上下文注入

保留三个内置工具（对齐 native 的四工具集，砍掉 `blueprint_create`）：

| 工具 | 作用 | 必要性 |
|---|---|---|
| `blueprint_update` | 把任务标记为 completed / skipped / in_progress | **必需**：脚本模式下模型在一次调用内完成实现后必须回写状态，否则跨调用无法推进 |
| `blueprint_status` | 读当前计划进度与活动阶段/任务 | 对齐 native |
| `blueprint_next` | 取下一个可执行任务（含验收标准与文件目标） | 对齐 native |

- 三个工具均可被 `--exclude-tools` 关闭（对齐 046 的 `tdd_*` 逃生舱做法）；
- 在 `--blueprint` / `--plan-next` 两种「有计划上下文」的模式下，把当前阶段/任务上下文
  **每回合**注入系统提示词（对齐 native 的 `before_agent_start` 注入 + 046 的
  `pi-resolve-turn-system-prompt` 机制），注入块结构沿用 native 的
  `## Active Blueprint` / `### Current Phase` / `### Current Task` / 验收标准 /
  文件目标 / 验证门清单。

### 6. 输出形态

- print 模式：`--blueprint` / `--plan-status` 直接把计划 Markdown 写到 **stdout**；
  `--plan-next` 先打印取到的任务摘要再输出实现结果；`--plan-verify` 打印逐门结果。
  （修 native 的 print 空输出缺陷，实测缺陷 1；与 044 偏差 #15 / 045 偏差 #17 /
  046 偏差 #21 同源。）
- JSON 模式：stdout 保持**纯 JSONL**（事件序列与既有实现完全一致：
  `session → agent_start → turn_start → message_start/end（×N）→ turn_end → agent_end →
  agent_settled`），计划与进度摘要写 **stderr**（对齐 045/046 的 stdout/stderr 分流）。
- 未进入 blueprint 流程时行为**零变化**。

### 7. 与现有三阶段流程的互补关系（本任务的核心定位）

本项目既有流程（PI_PLAN §2「提交规范」）：**PLAN 建档 → 开发 → REVIEW 代码 →
REVIEW 验收**；每个任务编号对应一份 `tools/pi/devel/<编号>.md` 任务文档。

blueprint 处在**开发阶段之前**，把一个高级目标拆成「阶段 → 任务」，让每个任务
恰好等于一次既有三阶段流程：

```
blueprint 目标
  └─ 阶段 phase（2-6 个，依赖序：基础先行）
       └─ 任务 task（每阶段 2-8 个，每个 = 一次会话 = 一次既有三阶段流程）
            ├─ PLAN 建档：tools/pi/devel/<编号>.md
            ├─ 开发：实现 + 测试
            └─ 验收：bin/gf fmt / git diff --exit-code / bin/gf check / 相关测试
```

对应关系：

| blueprint 概念 | 既有流程对应物 |
|---|---|
| 阶段 phase | 一批相关任务编号（如 047-052） |
| 任务 task | 一个任务编号 = 一份 `devel/<编号>.md` + 一次开发 + 一次验收 |
| 任务 acceptance_criteria | 该任务文档的「验收点」逐条 |
| 任务 file_targets | 该任务文档的「任务相关的代码文件」 |
| 阶段 verification_gates | 既有门禁命令：`bin/gf check` / `bin/gf fmt --check` / 相关测试 |
| `.pi/blueprint.md` | 计划全景（既有 `devel/<编号>.md` 是单个任务的人工可读产物） |

因此 `--plan-verify` 的 `custom_command` 门禁建议直接写既有门禁，例如
`bin/gf check && bin/gf fmt --check`。反过来，blueprint 状态文件里记录的任务 ID
（`1.1` / `2.3`）与既有三位编号体系（`047`）不同构——**不强行合并**：blueprint 的
`phase.task` 是会话内序号，既有编号是仓库内全局号；`--plan-next` 输出任务时同时
提示「本任务对应一次新的三阶段流程（先建档、再开发、后验收）」，由执行者决定分配
哪个三位编号。

### 8. 安全与既有规范

- 所有门禁命令走 `(liii subprocess)` `run`，**必带 `:timeout`**；
- 状态只写工程内 `.pi/blueprint.*`，**不写 `~/.pi/` 任何目录**；
- 计划文件与日志不写凭据；日志不泄露 API key / 代理地址 / 请求体；
- 无凭据 / 超时 / 网络失败按既有错误规范报错并退出码 1；
- 单文件不超过 300 行（`bin/gf check` 硬约束），子库再拆子模块。

## 验收点

1. **CLI 形态与参数解析**：
   - `--blueprint` / `--plan-status` / `--plan-next` / `--plan-verify` / `--plan-abandon`
     五个开关被正确解析（`parse-pi-args` 返回对应键为真）；
   - 五个开关互斥，同时给出时报可读错误并退出码 1；
   - `--blueprint` 与 `--code-review` / `--simplify` / `--red-green` 互斥，报可读错误
     并退出码 1；
   - `--approve` 只允许与 `--plan-verify` 同用，单独给出时报可读错误并退出码 1；
   - `--blueprint` 但无目标描述（无消息、无 `@file`）时报可读错误并退出码 1；
   - `--blueprint-file <path>` 覆盖状态文件路径（便于测试隔离）。
2. **计划生成（结构化输出 + 确定性校验）**：
   - 提示词结构对齐 native（2-6 阶段、每阶段 2-8 任务、任务含 title/description/
     acceptance_criteria/file_targets/dependencies、任务 ID 形如 `phase.task`、
     每阶段带验证门）；
   - 模型输出的 JSON 被正确解析为阶段/任务/门禁结构；
   - 任务 ID 重复、依赖指向不存在的任务、**依赖成环**、阶段/任务数量越界、
     门禁类型非法（`tests_pass` / `typecheck_clean`）时，报可读错误并退出码 1，
     **不落盘**；
   - 校验通过时落地 `.pi/blueprint.json` + `.pi/blueprint.md`。
3. **依赖跟踪**：
   - 创建即重算阻塞：依赖未满足的任务状态为 `blocked`，无依赖的任务为 `pending`，
     跨阶段依赖同样生效；
   - 完成某个任务后，依赖它的任务由 `blocked` 回到 `pending`；
   - `blueprint_next` 只返回**依赖全部完成**的任务（就绪判定）；
   - 全部任务完成且全部阶段门禁通过时，blueprint 状态置 `completed`。
4. **验证门**：
   - `custom_command` 门在当前工作目录执行，**必带 `:timeout`**；
   - 门禁通过 → 记录 `passed=true` + `last_checked_at`，阶段推进（`verified`），
     活动阶段前移到最后阶段时 blueprint 置 `completed`；
   - 门禁失败 → 记录 `passed=false` + 错误摘要（不抛未捕获异常），阶段**不**推进，
     命令行报告失败并退出码 1；
   - `user_approval` 门：不带 `--approve` 时报告「仍需人工确认」且不推进；
     带 `--approve` 时标记为通过并推进（不再死锁）；
   - 门禁类型为 `tests_pass` / `typecheck_clean` 时报可读错误，**绝不静默改跑 npm**。
5. **上下文注入**：
   - `--blueprint` / `--plan-next` 模式下，每回合注入当前阶段/任务上下文
     （含验收标准、文件目标、当前阶段门禁清单）；
   - 注入按回合生效（与 `--auto-review` / `--red-green` 同款
     `pi-resolve-turn-system-prompt` 机制）。
6. **内置工具**：
   - `blueprint_update` 能把任务标记为 completed / skipped / in_progress，并回写状态文件；
   - `blueprint_status` 返回计划进度、活动阶段与活动任务；
   - `blueprint_next` 返回下一个可执行任务（含验收标准与文件目标）；
   - 三个工具可用 `--exclude-tools` 关闭，关闭后不影响主流程。
7. **输出形态**：
   - print 模式：计划 Markdown / 进度摘要 / 门禁结果写 stdout；
   - JSON 模式：stdout 为纯 JSONL（事件序列与既有实现一致：
     `session → agent_start → turn_start → message_start/end（×N）→ turn_end →
     agent_end → agent_settled`），计划与进度摘要写 stderr；
   - 未进入 blueprint 流程时行为零变化（既有 `bin/gf pi` 输出与事件完全不变）。
8. **边界与安全**：
   - 状态只写工程内 `.pi/blueprint.*`，**不写 `~/.pi/` 任何目录**；
   - 无活动计划时 `--plan-status` / `--plan-next` / `--plan-verify` / `--plan-abandon`
     打印 `No active blueprint.` 并以退出码 0 结束；
   - 无凭据 / 超时 / 网络失败按既有错误规范报错并退出码 1；
   - 日志不泄露 API key、代理地址与请求体；所有外部命令与网络 IO 均带超时。
9. **回归与门禁**：
   - `bin/gf pi` 既有测试全绿；新增单元测试镜像源码库结构（一个函数一个测试文件）；
   - `xmake b goldfish` → `bin/gf fmt` → `git diff --exit-code` → `bin/gf check`
     → `bin/gf doc --build-json` 依次通过；单文件不超过 300 行。

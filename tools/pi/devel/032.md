## 日期 任务描述

### 2026-10-19 任务建档（pi，glm/glm-5.3-flash）

#### What

1. 查阅 `PI_PLAN.md` §3 任务 032 验收点：settings.json 的 `retry.provider.maxRetries`
   （本机=12，用于扛 429 provider 级错误窗口）未被消费，bin/gf pi 只读顶层
   maxRetries=3 导致 429 快速失败；先核查现有重试对 429 是否已足够，确认有缺口才
   实现，否则按用户裁定降级关闭。
2. 从 `tools/pi/devel/ddd.md` 模板复制建立 `tools/pi/devel/032.md` 任务文档。
3. 完成初步核查（结论见 How），为开发阶段提供实现/降级判定依据。

#### Why

- Node pi 的重试分两层：provider 级错误（API 网关 429/5xx 等）走
  `retry.provider.maxRetries` 长预算（本机=12），模型级错误走顶层
  `retry.maxRetries=3`。bin/gf pi 若只消费顶层 3 次，gemini 429 突发窗口内
  （指数退避 base 2000ms：约 2s+4s+8s 即耗尽）会快速失败，与 Node pi 行为不对齐。

#### How

- 核查结论（开发阶段起点）：
  1. **缺口确认存在**：`tools/pi/liii/pi/config.scm` 的 `%build-retry-record` 只读取
     enabled/maxRetries/baseDelayMs/maxAgentDelayMs，嵌套 `provider` 对象被直接丢弃；
     `pi-retry-config` record（types.scm/record.scm）无 provider 字段。
  2. `pi-resolve-retry-params`（retry.scm）仅从 `retry` 节取 `max-retries`（缺省 3），
     无 provider 预算概念。
  3. 消费方（gemini/request.scm 等）对所有 retriable 状态码（429/5xx/408/409/0）
     使用单一 max-retries 预算，429 走 3 次快速失败，与本机 settings 的 12 次预算
     不符——即任务表所述差距属实，非"已支持"。
- 实现路径（若开发阶段确认做）：record 增加 provider-max-retries 字段 →
  `%build-retry-record` 解析 `provider.maxRetries`（缺省回退顶层值）→
  `pi-resolve-retry-params` 返回 provider 预算 → 重试循环中 retriable HTTP 错误
  使用 provider 预算。429 退避窗口是否同步放大（如 provider 级 baseDelay）留待
  开发阶段与用户确认。
- 降级关闭路径（若开发阶段核查认为影响小）：任务状态改已完成，032.md 记录
  "gemini 429 快速失败影响可接受"的裁定依据，不改代码。

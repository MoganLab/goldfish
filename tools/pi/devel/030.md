## 2026-10-19 任务描述

### What

1. 阅读 `PI_PLAN.md` §3 任务 030 的验收点与 `PI_SPEC.md` 中的 MiniMax TODO
   段（含 `--provider minimax` 预期用法与已知阻塞描述）。
2. 核对本机事实：auth.json 中 `minimax`/`minimax-cn` 均为 `type: "api_key"`、
   key 前缀 `sk-cp-`；models-store.json 中 minimax 目录为 M2.7 / M2.7-highspeed
   / M3（国际站 `api.minimax.io`），models.json 用户自定义追加 `MiniMax-M3.1-Flash`
   且 provider baseUrl 为大陆站 `https://api.minimaxi.com/anthropic`。
3. 从 `tools/pi/devel/ddd.md` 模板复制建立 `tools/pi/devel/030.md`：填写状态、
   预计改动的实现/测试文件、验收点（含 M3.1 Flash 覆盖与工具调用冒烟）、
   测试方法与门禁流程。
4. 明确开发期的关键决策点：`minimax` 与 `minimax-cn` 别名关系、端点归一化
   （store 内模型级 baseUrl 指向国际站，需按用户要求落到大陆站）、
   thinking/cache 字段兼容性裁剪。

### Why

- 用户裁定（2026-10-19）：030 为 033 完成后的下一个优先任务；MiniMax M3.1
  Flash 特别快，030 完成后轮换池主力使用 minimax m3.1-flash。
- `bin/gf pi` 此前仅支持 google/anthropic/kimi-coding/glm/deepseek；MiniMax
  在 auth.json 与 models-store 中已有条目，但无 provider 实现，属新增链路，
  工作量大于 028/029（两者为既有链路的目录/配置补齐）。

### How

- 新增 `(liii pi minimax)` 薄封装复用 `(liii pi anthropic)` 全套协议实现
  （与 `deepseek.scm` 同型），避免重复实现 SSE/工具调用解析；provider 专属差异
  （端点、thinking 字段、usage 字段差异）在封装层或 `models.scm` 元数据层处理。
- 路由三处对齐：`auth.scm`（env key 与 auth.json 别名回退）、`models.scm`
  （默认端点与 baseUrl 归一）、`agent.scm`（provider → request-stream 分发）。
- 模型目录两处对齐：`models/builtin.scm`（无 models-store 时的兜底目录）与
  fixture `models.json`（TDD 依赖），保证 `--list-models` 与
  `pi-route-provider-and-model` 在真实目录与测试 fixture 下都命中。
- 遵循 TDD：先补 minimax 薄封装单测与目录/路由/元数据断言，再接线实现；
  真实冒烟通过后由 Claude 更新 `PI_SPEC.md`。

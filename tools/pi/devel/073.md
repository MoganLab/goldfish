## 验收点

从 `tools/pi/Agents.md` §3 任务表 073 提取并细化：

1. **动态 Flags 挂载与解析支持**：
   - 扩展可通过 `register-flag!`（或扩展 API）声明自定义 CLI flags（支持布尔 flag、单值 option、参数别名、默认值及 handler/validator）；
   - `args.scm` 的 `parse-pi-args` 支持依据当前活跃扩展注册表（`current-extension-registry`）动态提取扩展 flags 和默认值，正确解析命令行并填入参数表中；
   - 动态 flags 支持短选项、长选项及带参选项（如 `--ref <val>`, `--ref=<val>` 等）；
   - 支持动态注册参数验证规则（validator），在参数校验阶段安全调用并输出可诊断错误信息。
2. **Local Flow 与 Command 路由分发解耦**：
   - 扩展可注册 local-flow 处理器（如 blueprint local flow、compass local flow）或 command 路由处理器；
   - `modes.scm` 的 `dispatch-pi` 彻底移除对 `(pi-compass-local-flow? ...)`、`(pi-blueprint-local-flow? ...)`、`(pi-blueprint-flag? ...)`、`--simplify`、`--red-green` 等特定扩展的硬编码 cond 分支；
   - 路由分发统一遍历活跃注册表中的 local-flow / command 处理器，按注册顺序或匹配规则优先命中并执行，未命中时回退至默认 agent/print/json 会话流；
   - 保证所有 local-flow 行为（退出码、控制台输出、执行参数）与既有行为 100% 保持兼容。
3. **移除核心层硬编码与解耦收敛**：
   - 移除 `args.scm`、`cli.scm`、`modes.scm` 中直接 import `(liii pi blueprint args)`、`(liii pi compass args)` 等硬编码依赖；
   - 移除 `cli.scm` 中 `%run-pi-main` 针对 `--red-green`、`--blueprint` 等扩展标志的硬编码校验分支；
   - 保持所有既有 CLI 参数与 local-flow 行为 100% 兼容。
4. **严格代码规模与门禁控制**：
   - 严格遵守 <= 300 行硬约束：`tools/pi/liii/pi.scm`（当前 299 行）、`tools/pi/liii/pi/tools.scm`（当前 293 行）、`tools/pi/liii/pi/args.scm`（当前 276 行）；
   - 新增门面导出下沉到 `(liii pi extension)` 等已有子模块，绝不硬塞入 `tools/pi/liii/pi.scm`；若 `args.scm` 面临超限，及时拆分出子模块（如 `(liii pi args validator)`）；
   - 单元测试 TDD 覆盖动态 flags 与 local flow 路由分发；

## 2026-10-20 任务描述

### What

1. 依据 `Agents.md` 任务 073 规格，从 `tools/pi/devel/ddd.md` 建立 PLAN 任务文档 `tools/pi/devel/073.md`；
2. 梳理 `args.scm`、`cli.scm` 与 `modes.scm` 中对各扩展（blueprint, compass, simplify, red-green 等）的硬编码引用点与依赖耦合；
3. 设计扩展注册表驱动的动态 Flags 解析方案：扩展声明 flags（名称、类型、默认值、参数个数）、defaults 注入与动态选项消费；
4. 设计通用 Local Flow 与 Command 分发机制：让扩展注册自身的前置流程判断与执行逻辑，核心层仅保留统一路由链；
5. 针对 `pi.scm`（299 行）、`tools.scm`（293 行）、`args.scm`（276 行）制定代码行数控制方案，避免超限。

### Why

原生 pi 的 Extension 机制不仅提供动态工具，还允许扩展挂载 flags、命令与拦截前置流程。主仓库目前在 `args.scm`、`cli.scm` 和 `modes.scm` 中硬编码了大量特定扩展的分支判断和 import，违背了 Extension 体系的解耦原则，也直接阻碍了后续任务（075 内置扩展收敛与 077 外部扩展剥离）。必须将参数解析与路由分发完全解耦为动态注册机制。

### How

1. **Flag 扩展能力强化**：在 `(liii pi extension types)` 与 `(liii pi extension registry)` 中完善 `extension-flag-def`，使其支持 `aliases`（如 `-h`, `--help`）、`takes-arg?` / `arity`、`validator` 与 `default`；支持注册 flow 处理器（`register-flow!` 或 `register-command!`）。
2. **动态参数解析**：在 `args.scm` 中，`parse-pi-args` 查询当前活跃扩展注册表，合并动态 flags 规则与默认值；在遇到未被基础内置选项匹配的 flag 时，在扩展注册表中查找匹配的扩展 flag 并按定义消费 1 或 2 个参数。
3. **Local Flow 注册与分发**：在扩展 API 中支持注册 flow 钩子，包含断言谓词 `(lambda (parsed) ...)` 与执行处理器 `(lambda (parsed cfg mode initial-msg) ...)`. `modes.scm` 的 `dispatch-pi` 遍历注册表中的 flows，优先命中即分发执行。
4. **平滑过渡与行数控制**：拆分或精简 `args.scm` 中的辅助逻辑（可抽离出子模块如 `args/validator.scm`），确保 `args.scm` 与 `pi.scm` 均严格低于 300 行硬约束。

### (liii http) 响应头获取方式核实（开发前必读）

建档阶段核实了 `goldfish/liii/http.scm` 及 C++ 底层 `src/liii_http.cpp` 实现：

1. **结构与类型**：`http-post` 无论普通模式还是流式（callback）模式，底层
   `cpr::Response` 均通过 `response2hashtable` 转换为 Scheme hash-table：
   - 响应对象 `resp` 的 `'headers` 键对应一个子 hash-table。
   - 所有 header 键名在放入该子 hash-table 时均经 `tolower` 转为**小写字符串**
     （如 `"retry-after"`），值为字符串（如 `"5"` 或 `"120"`）。
   - 获取方式：若 `resp` 为 hash-table，调用 `(hash-table-ref resp 'headers #f)`
     或 `(resp 'headers #f)`；在 headers 子表中调用
     `(hash-table-ref headers "retry-after" #f)` 或 `(headers "retry-after" #f)`。
2. **异常与容错**：在网络抛出异常时，底层 `error2hashtable` 返回的 hash-table
   无 headers 键；或各 provider 的 catch 块返回模拟 alist（如 `((status-code . 0) ...)`）。
   因此响应头提取必须防御性容错（非 hash-table 或无 headers 键时安全返回 `#f`）。
3. **结论**：主库 `goldfish/` 的 `(liii http)` 机制已完整提供响应头能力，
   **本任务不需要改动任何 `goldfish/` 主库代码**，所有增强纯在 `tools/pi/` 内实现。

## 验收点

从 `PI_PLAN.md` §3 任务表 053 复制并细化为可验证项：

1. **Retry-After 头提取与解析**：
   - 支持从 `(liii http)` 响应 hash-table 中安全提取小写键 `"retry-after"`；
     在响应为 alist、无 headers 或异常时静默回退为 `#f`。
   - 解析支持合法秒数字符串（整数与小数），安全转换为秒数；
   - 畸形字符串、负数、无效格式安全回退为 `#f`，不抛未捕获异常。
2. **延迟计算与合理钳制（Clamp）**：
   - 优先采用有效 Retry-After 值；若无则采用指数退避（`base-delay-ms * 2^(attempt-1)`）。
   - 下限钳制：延迟不得低于合理下限（如 0.1s），防止 0 秒紧密死循环冲击服务；
   - 上限钳制：延迟不得高于 `max-agent-delay-ms`（默认 60s），防止服务端返回
     过大秒数（如 86400）导致 agent 进程假死挂起。
3. **重试 stderr 脱敏日志可见性**：
   - 发生 retriable error（408, 409, 429, 500, 502, 503, 504, 529, 0 等）且决定重试时，
     在 `(current-error-port)` 输出单行结构化脱敏摘要；
   - 日志包含：状态码、当前重试轮次与上限（如 `attempt 1/3`）、等待延迟秒数，
     并在有 Retry-After 时明确标出；
   - **绝对脱敏**：严禁出现 API key、URL query 参数、请求体、用户 prompt 或响应正文。
4. **三 provider 统一接入**：
   - `gemini`、`kimi`、`anthropic` 各自的 `request.scm` 与 `stream.scm`（共 6 处），
     全部接入 Retry-After 解析、统一延迟计算与 stderr 脱敏日志；
   - 彻底清除 `kimi/stream.scm` 与 `anthropic/stream.scm` 中硬编码的 `(sleep 1.0)`，
     消除 `kimi/request.scm` 与 `anthropic/request.scm` 中重复的私有 `%calc-delay-sec`。
5. **既有行为不回归**：
   - 既有 multikey 轮换逻辑（429/403 换 key）与耗尽判定不受影响；
   - 既有非重试状态码（200 成功、400 参数错等）行为完全一致；
   - 全量回归测试通过，既有测试零失败。
6. **门禁通过**：`timeout 600 xmake b goldfish`、`bin/gf fmt`（无 diff）、
   `git diff --exit-code`、`bin/gf check`、`bin/gf doc --build-json` 全绿；
   300 行文件约束不破坏。

## 2026-10-20 任务描述

### What

1. 建立 053 任务文档，核实 `(liii http)` 响应头获取方式并确定纯 `tools/pi` 改造范围；
2. 在 `(liii pi retry)` 中实现 `pi-extract-retry-after`、`pi-parse-retry-after`、
   带 Retry-After 与上下限钳制的 `pi-calc-retry-delay`、以及 `pi-log-retry` 脱敏输出；
3. 将 gemini / kimi / anthropic 的 request 与 stream 统一接入新的重试计算与日志；
4. 补充单元测试镜像目录结构与 053.scm 验收脚本。

### Why

- 2026-10-20 实测 minimax 频繁出现 529 服务过载，现有多 provider 重试实现不一致
  且缺乏 stderr 提示，导致排查 429/529 频率困难；
- 服务端通常通过 Retry-After 指示建议等待时间，忽略该响应头会导致要么等待时间过长、
  要么重试过急加剧服务端限流，引入 Retry-After 能显著提升 agent 的重试质量和韧性。

### How

- 响应头提取利用 `(liii http)` 现有的 headers hash-table 小写 key 特性；
- 延迟计算统一采用：
  `delay = clamp(retry-after-or-backoff, min-delay-sec, max-delay-sec)`；
- stderr 输出经由 `(current-error-port)` 格式化，单行日志规整且经过严格脱敏验证。

### 命令面（实测）

| 原生命令 | 行为 | 实测 |
|---|---|---|
| `/tdd <task>` | 激活 TDD 会话（RED 阶段），并向会话追加一条 follow-up 用户消息：`Implement the following using TDD (red-green-refactor): <task>` | ✓（消息原文见 RPC 事件流） |
| `/tdd`（无参数） | 显示当前状态摘要 | ✓ |
| `/tdd off` | 停用：`state.json` 置为 idle、`history.jsonl` 追加一条周期记录 | ✓（实测 state.json 归零、history.jsonl 增加一行） |

三个内置工具（模型可调用）：`tdd_status`（查状态）、`tdd_advance`（手动推进阶段，
自动检测失灵时的逃生舱）、`tdd_reset`（重置为 idle 并记录周期）。

### 实测：一次完整 RED-GREEN-REFACTOR 周期

`pi -p "/tdd ..."` 的 print 模式不可用（见「实测缺陷」第 1 条），故用
`pi --mode rpc` 驱动同一会话（`--no-session --no-context-files`），事件流全量记录于
`~/pi-redgreen-sandbox/rpc-run1.jsonl`。工具调用顺序（实测）：

1. `bash ls -la` / `read calc.py` / `read test_calc.py`（探查现状）
2. `bash pytest`（基线：1 passed）
3. `edit test_calc.py`（**先写测试**：补 4 个 `is_even` 用例）
4. `bash pytest` → `5 failed`（`AttributeError: module 'calc' has no attribute 'is_even'`）
   → RED 达成（测试因功能缺失而失败）
5. `tdd_status` → `tdd_advance`（模型自述理由："Auto-detection missed test run"）
6. `edit calc.py`（**最小实现**：`def is_even(n): return n % 2 == 0`）
7. `bash pytest` → `6 passed` → `tdd_status` → `tdd_advance`
8. `edit test_calc.py`（**重构**：清理 import）→ `bash pytest` → `6 passed` → `tdd_advance`
9. `bash git status` / `bash git diff`（收尾自查）

最终 assistant 文本按 RED / GREEN / REFACTOR 三段总结，与 native 的阶段语义一致。

**结论**：TDD 顺序确实被强制（先测试后实现、再重构），但强制来自**系统提示词注入**
（`before_agent_start` 事件把阶段提示词追加到 system prompt 末尾，★ `tdd-injector.ts`），
**不是工具级硬门禁**。

### 实测缺陷（三条，均有源码依据）

1. **print 模式空输出**：`pi -p "/tdd <task>"` 退出码 0、**stdout 为空**。扩展用
   `pi.sendUserMessage(..., {deliverAs: "followUp"})` 派发任务（★ `tdd-command.ts`），
   print 模式不等待异步 follow-up 回合（与 044 偏差 #15、045 偏差 #17 同源）。
   实测：state.json 写入 `phase=red`，但沙箱文件零改动、agent 回合未执行。
2. **自动阶段推进失效**：扩展在 `tool_execution_end` 里按 `{stdout, stderr, exitCode,
   command}` 形状读 bash 结果（★ `index.ts` 的 `extractBashResult`），而 pi 0.85.1 的
   bash 工具结果实测是 `{"content":[{"type":"text","text":"..."}],"details":{...}}`
   ——字段全部落空 → `command` 为空 → 不被识别为测试命令 → `last_test_run` 恒为
   `null`、阶段**不自动推进**。实测：模型被迫三次调用 `tdd_advance` 手动推进。
3. **文件顺序追踪失效（ordering_enforcement 形同虚设）**：`extractFilePath` 期望结果
   里有 `file_path` / `path` 字段（★ `index.ts`），实测 edit 结果是
   `{"content":[{"type":"text","text":"Successfully replaced 1 block(s) in test_calc.py."}],
   "details":{"diff":"..."}}` → 路径取不到 → `test_files` / `impl_files` 恒为空 →
   RED 阶段的顺序告警（★ `prompts/warnings.ts`：`TDD Warning.` /
   `TDD Violation (strict mode).`）**永不触发**。实测 state.json 中 `impl_files` 为空，
   而模型确实编辑过实现文件 `calc.py`。

### 提示词与配置（★ 源码原文）

- 三阶段提示词：★ `src/prompts/{red,green,refactor}-phase.ts`
  - RED：`## TDD: RED Phase -- Write Failing Tests`（写失败测试、每测只断言一件事、
    用真实代码不用 mock、**写完必须跑并确认因功能缺失而失败**、含「Rationalization
    Prevention」反借口表与三步 Verification Gate）
  - GREEN：`## TDD: GREEN Phase -- Make Tests Pass`（最小实现、不加需求外特性、
    不重构其他代码、写完必须跑并确认通过）
  - REFACTOR：`## TDD: REFACTOR Phase -- Improve Without Breaking`（保持测试绿、
    不加新行为、每次重构后跑测试、破坏测试立即回滚、可选阶段）
- 注入块还可能附带两条告警（★ `tdd-injector.ts`）：陈旧测试结果告警（上次测试运行
  发生在更早回合）、顺序告警（RED 阶段先改实现文件，因缺陷 3 实际不触发）。
- 配置 `~/.pi/red-green/config.json`（★ `config.ts`）：`injection_mode`
  （`active-only` 默认 / `always` / `nudge` / `off`）、`ordering_enforcement`
  （`warn` 默认 / `strict` / `off`）、`auto_advance`（默认 true）、
  `coverage_threshold`（80）、`coverage_enabled`（false）、`test_file_patterns`
  （按语言）、`test_runner_patterns`（默认 14 条命令关键字）。
- 测试文件分类规则（★ `file-classifier.ts`）：先排除配置类扩展名与配置文件名
  （`package.json` / `tsconfig*` / `Makefile` / `pyproject.toml` 等），再按语言匹配
  `test_file_patterns`（`*.test.ts` / `test_*.py` / `*_test.go` / `tests/**` 等），
  命中为 test，否则为 implementation。
- 测试运行检测（★ `test-run-detector.ts`）：命令关键字命中 `test_runner_patterns`
  后，按 vitest/jest、pytest、go test、cargo test 四种解析器从输出提取
  passed/failed/errors 计数。

## 形态裁定

脚本模式无 TUI、无斜杠命令、无跨会话状态，映射为 **CLI 开关 + 单次调用内的阶段机**：

```bash
# 以 TDD 强制模式执行一次任务（RED→GREEN→REFACTOR 在一次调用内自动推进）
bin/gf pi --red-green "实现用户登录功能"
```

关键裁定点：

1. **一个开关走完一个周期**：native 的 `/tdd` 是 TUI 会话级开关（跨回合、跨会话
   持久化）；脚本模式一次调用即一个完整 TDD 周期——阶段在**进程内**推进，调用结束
   即产出阶段摘要。`--red-green` 与 `--code-review` / `--simplify` 互斥（报错退出码 1）。
2. **硬门禁（超出 native）**：RED 阶段对**实现文件**的 `edit` / `write` 直接拒绝
   （返回工具错误，提示"先写失败测试"）；测试文件不受限。native 只有提示词级约束，
   且其顺序追踪因缺陷 3 完全失效——这是本任务"强制"二字的核心价值。
3. **自动阶段推进（修 native 缺陷 2）**：`bin/gf pi` 自己掌握 bash 工具结果形状，
   从输出解析 pytest / vitest / jest / go test / cargo test 摘要判定
   pass / fail / error，按状态机自动推进 RED→GREEN→REFACTOR→COMPLETE；
   阶段不匹配时注入告警（对应 native 的 `advancePhase` warning 文案）。
4. **零外部状态**：不写 `~/.pi/red-green/`，状态只存在于进程内（对齐「`~/.pi/agent/`
   只读复用」与「会话不写入用户目录」的既有约定）。print 模式在结束时输出阶段摘要；
   JSON 模式把摘要写 **stderr**（stdout 保持纯 JSONL），事件序列不变。
5. **逃生舱**：提供 `tdd_status` / `tdd_advance` / `tdd_reset` 三个内置工具（对齐
   native），模型在自动检测失灵时可手动推进或重置；可用 `--exclude-tools` 关闭。
6. **提示词注入沿用 native 三段结构**（★ 原文改写为 Scheme 字符串常量），按当前阶段
   每回合注入（native 在 `before_agent_start` 注入，等价于本项目的
   `pi-resolve-turn-system-prompt` 每回合系统提示词机制，与 `--auto-review` 同款接线）。
7. **缺任务描述即报错**：`--red-green` 但初始消息为空时，报可读错误并退出码 1。

### 行为要点

- 自动推进：RED + 失败 → GREEN；GREEN + 全通过 → REFACTOR；REFACTOR + 全通过 →
  COMPLETE；不匹配转移停留原阶段并把告警写入状态，下一回合随提示词注入；
  阶段历史完整记录。
- 硬门禁：RED 阶段 `edit`/`write` 指向实现文件时直接返回错误工具结果（不落盘、
  不抛未捕获异常），测试文件与配置文件放行。
- 摘要：print 模式在 assistant 文本后输出；JSON 模式写 stderr，stdout 保持纯 JSONL。
- 零外部状态：TDD 状态仅存于进程内，不写 `~/.pi/` 下任何目录。

## 验收点

1. **CLI 形态与参数解析**：
   - `--red-green` 被正确解析（`parse-pi-args` 返回 `red-green` 为真）；
   - `--red-green` 与 `--code-review` / `--simplify` 互斥，报可读错误并退出码 1；
   - `--red-green` 但无任务描述（无消息、无 `@file`）时报可读错误并退出码 1；
   - 未知选项进入既有 unknown-flags 处理，不静默吞掉。
2. **阶段提示词注入**：
   - RED 阶段注入块含任务描述、规则（先写失败测试 / 写完必须跑并确认因缺失而失败）
     与验证门三要素；
   - 阶段推进后注入块随之切换为 GREEN（最小实现、跑测试确认通过）/ REFACTOR
     （不破坏测试、可选阶段）措辞；
   - 注入按回合生效（与 `--auto-review` 同款 `pi-resolve-turn-system-prompt` 机制）。
3. **测试运行检测与阶段自动推进**：
   - 从 bash 工具输出解析 pytest / vitest / jest / go test / cargo test 摘要，
     得到 passed / failed / errors 计数；
   - RED + 存在失败 → GREEN；GREEN + 全通过 → REFACTOR；REFACTOR + 全通过 → COMPLETE；
   - RED + 全通过 → 停留 RED 并给出「测试的是既有行为」告警；
   - GREEN + 仍失败 → 停留 GREEN 并给出「继续实现」告警；
   - REFACTOR + 失败 → 停留 REFACTOR 并给出「重构破坏了测试，请回滚」告警；
   - 阶段历史被完整记录（进入时间 + 阶段序列）。
4. **顺序强制门禁**：
   - RED 阶段对**实现文件**的 `edit` / `write` 调用被拒绝，工具结果为错误并带可读
     提示（要求先写失败测试）；**测试文件**的写入不受限；
   - 分类按语言模式表判定（至少覆盖 scheme `*-test.scm` / `tests/**`、python
     `test_*.py` / `*_test.py`、typescript `*.test.ts` / `*.spec.ts`、go `*_test.go`、
     rust `tests/**`），配置文件（`package.json` / `tsconfig*` / `pyproject.toml` 等）
     归为 other 不受限；
   - 门禁拒绝不产生未捕获异常，agent 循环继续（模型收到错误后自行纠正）。
5. **状态摘要输出**：
   - print 模式在 assistant 文本之后输出 TDD 阶段摘要：当前阶段、阶段历史、
     测试文件列表、实现文件列表、最后一次测试运行结果（passed/failed/errors）；
   - JSON 模式摘要写 stderr，stdout 保持纯 JSONL，事件序列与既有实现一致
     （`session → agent_start → turn_start → message_start/end（×N）→ turn_end →
     agent_end → agent_settled`）；
   - 未进入 TDD 模式时行为零变化（既有 `bin/gf pi` 输出与事件完全不变）。
6. **内置工具（逃生舱）**：
   - `tdd_status` 返回当前阶段/任务/文件历史/测试结果/是否陈旧；
   - `tdd_advance` 手动推进到下一阶段（idle 时报错「无活动 TDD 会话」）；
   - `tdd_reset` 重置为 idle 并记录本次周期；
   - 三个工具可用 `--exclude-tools` 关闭，关闭后不影响主流程。
7. **边界与安全**：
   - 零外部状态文件写入（不写 `~/.pi/` 任何目录）；
   - 无凭据 / 超时 / 网络失败按既有错误规范报错并退出码 1；
   - 日志不泄露 API key、代理地址与请求体；
   - 所有外部命令与网络 IO 均带超时。
8. **回归与门禁**：
   - `bin/gf pi` 既有测试全绿；新增单元测试镜像源码库结构（一个函数一个测试文件）；
   - `xmake b goldfish` → `bin/gf fmt` → `git diff --exit-code` → `bin/gf check`
     → `bin/gf doc --build-json` 依次通过；单文件不超过 300 行。

### Why

任务 044-049 是一组「原生 pi 扩展 → `bin/gf pi` 脚本模式对应能力」的任务，
用户裁定必须先有原生 pi 的可运行对照基准，再实现脚本模式对应形态。
red-green 与 044/045 共享「提示词构造 + 报告输出」，但关注点不同：044 找**缺陷**、
045 找**可简化点**，red-green 管的是**开发过程的顺序纪律**——先写失败测试、
再最小实现、最后重构。对照还暴露出 native 扩展在 pi 0.85.1 下的三处失效
（自动推进、顺序追踪、print 空输出），脚本模式可以把「强制」做成真正的
工具级门禁，而不是仅靠提示词。

### How

1. **状态机**：`(liii pi red-green state)` 用 alist 记录 phase / task /
   test_files / impl_files / last_test_run / phase_history，转移表按 native 的
   `advancePhase` 语义移植（red+fail→green、green+pass→refactor、
   refactor+pass→complete，不匹配转移返回告警文案）；
2. **检测**：`(liii pi red-green detect)` 从 bash 工具输出文本解析四种 runner 的
   摘要计数（本项目 bash 工具把 stderr 合并进 stdout，非零退出码以
   "Command exited with code N" 出现在文本中，据此区分 error 与 fail）；
3. **分类**：`(liii pi red-green classify)` 用按语言的模式表把路径判为
   test / implementation / other，模式表取自 native 默认值并补 scheme 约定；
4. **门禁**：`(liii pi red-green gate)` 在工具执行前判定——RED 阶段且目标是
   implementation 文件时返回错误工具结果（要求先写失败测试），不落盘；接线点在
   `(liii pi agent tools)` 的 `pi-execute-one-tool-call`；
5. **注入**：`(liii pi red-green prompt)` 提供三阶段提示词常量与注入块构造，
   经 `pi-resolve-turn-system-prompt` 每回合注入（与 `--auto-review` 同款）；
6. **接线**：`args.scm` 解析 `--red-green` 与互斥校验 → `modes/red-green.scm`
   分派 TDD 流程 → print/JSON 两种输出（摘要分流 stdout / stderr）；
7. **TDD**：先写单元测试（镜像源码结构、一个函数一个测试文件），再实现；
   验收脚本 `tools/pi/devel/046.scm` 逐条断言上述 8 组验收点。

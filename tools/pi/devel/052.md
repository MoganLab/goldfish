### 时钟来源复核（开发前必读）

计划原文提到 `time-utc->time-monotonic`。本文件建档时对仓库实际实现做了复核，
开发阶段以**实际可提供单调性**的来源为准：

| 候选 | 实测语义 | 是否可用 |
|---|---|---|
| `(liii time)` 的 `time-utc->time-monotonic` | 仅做 UTC→monotonic **类型转换**，`time-second` 仍是墙钟 epoch；不提供单调性 | 否（且 039 裁定 `(liii time)` 除 `sleep` 外不得使用） |
| `(liii time)` 的 `(current-time 'time-monotonic)` | 基于 `g-monotonic-nanosecond`，返回**自开机**秒/纳秒，单调 | 语义可用，但违反 039 的 `(liii time)` 禁用规则 |
| `(scheme time)` 的 `monotonic-nanosecond` | `std::chrono::steady_clock` 自开机纳秒；`(liii date-time current-time)` 已导入 `(scheme time)` | **推荐**：`(liii date-time)` 内部直接使用 |

关键结论：

- 单调钟的基准是**自开机**（本机实测 `monotonic-nanosecond` 约 `6.1e13` ns，
  远小于 Unix epoch），不是 Unix epoch；实现与测试都按「单调基准」理解，
  **不得**把它当作 epoch 时间戳展示或序列化。
- 「单调 epoch 基准」若指计划原文的验证结论，应按「单调、可用于差值比较的基准」
  落实；墙钟与单调钟的差值固定，混用会破坏超时语义。
- 墙钟 `pi-current-time-seconds` / `pi-current-time-millis` /
  `pi-iso-8601-utc-now` 保持原语义，仅用于时间戳展示与持久化；超时比较不再使用。

## 验收点

从 `PI_PLAN.md` §3 任务表 052 复制并细化为可验证项：

1. **date-time 单调 API**：`(liii date-time current-time)` 提供
   `current-monotonic-millis` / `current-monotonic-seconds`，并由
   `(liii date-time)` 导出；两者均返回**精确整数**，连续采样单调不减，
   量级为自开机基准（不等于墙钟 epoch），不依赖 `(liii time)`。
2. **pi 封装**：`(liii pi time)` 暴露 `pi-current-monotonic-seconds`，并经
   `(liii pi)` 门面可用；墙钟接口 `pi-current-time-seconds` /
   `pi-current-time-millis` / `pi-iso-8601-utc-now` 行为不变。
3. **agent 会话超时改用单调钟**：`agent.scm` 的 `start-sec` / `deadline-sec` /
   超时比较全部使用单调秒；墙钟不再参与会话超时判定；`--session-timeout`
   的负数立即超时、`0` 关闭、正数未超时三种既有语义不回归。
4. **三路流式空闲超时改用单调钟**：gemini / kimi / anthropic 的
   `last-activity` 与 `now` 全部使用单调秒；墙钟不再参与
   `(- now last-act)` 判定；空闲超时的错误消息、重试与退出路径不变。
5. **回拨安全**：系统墙钟回拨（NTP 回拨或手工改时）不再使空闲超时失效。
   由于测试环境通常不能真实修改系统时钟，采用「可注入/可模拟时钟的判定
   路径 + 静态门禁」双重验证：模拟墙钟从较大值跳到较小值时，超时判定仍按
   单调钟推进而触发；同时静态断言 agent 与三路 stream 的超时比较不再出现
   `pi-current-time-seconds`。若开发阶段可安全使用 `faketime` 等工具，
   则补一条真实回拨冒烟（非必需，不得因缺少该工具而阻塞验收）。
6. **TDD 覆盖**：先写失败测试（date-time 两个新函数、pi 封装、超时判定），
   再实现；新增测试不得引用三份计划文档，测试素材使用自建 fixture/纯函数输入；
   全部既有测试不回归。
7. **门禁通过**：`timeout 600 xmake b goldfish`、`bin/gf fmt`（无 diff）、
   `git diff --exit-code`、`bin/gf check`、`bin/gf doc --build-json` 全绿；
   300 行文件约束不破坏（超限则继续拆分）。

## 实施路径（计划）

1. **date-time 层**：在 `goldfish/liii/date-time/current-time.scm` 内用
   `(scheme time) monotonic-nanosecond` 实现：
   - `current-monotonic-millis` = `(quotient ns 1000000)` 或等价的 `floor`；
   - `current-monotonic-seconds` = `(quotient ns 1000000000)`；
   两者返回精确整数；导出到 `(liii date-time)`。若沿用 `(liii time)` 的
   `time-utc->time-monotonic`，必须先证明其单调性，否则不得使用。
2. **pi 封装层**：`pi/time.scm` 增加 `pi-current-monotonic-seconds`（内部转发
   `current-monotonic-seconds`），门面 `(liii pi)` 再导出；保留墙钟函数不动。
3. **超时消费方**：
   - `agent.scm`：`start-sec`/`deadline-sec`/比较改用
     `pi-current-monotonic-seconds`；
   - 三路 `stream.scm`：`last-activity`/`now` 改用
     `pi-current-monotonic-seconds`；错误消息中的秒数仍按配置的 idle 秒数输出。
4. **可测性与回拨验证**：优先把「是否超时」收敛为纯判定（输入
   `now`/`last`/`idle`），再让生产路径注入单调钟读数；测试用显式数值覆盖
   「墙钟回拨但单调钟前进」的场景。若无法注入，则以静态 grep + 单调性/量级
   测试作为回拨安全的证据，并在验收记录中说明。
5. **TDD 顺序**：先新增 date-time 测试（红）→ 实现（绿）→ 新增 pi 封装测试
   （红）→ 实现（绿）→ 补 agent/stream 防回归断言 → 全量回归。

注意点：

- 不要把单调钟数值写入 session/event 的 `timestamp` 字段（会变成开机时间）。
- 单调钟只用于**同一进程内**的差值比较；跨进程/持久化一律用墙钟。
- 秒级接口的粒度是 1 秒；若现有 idle 超时按整秒比较，行为保持不变；
  如需更细粒度可同时使用毫秒接口，但不得改变错误消息语义。
- 三路 stream 的 `(liii time)` import 仅为 `sleep` 保留，不得为了单调钟重新
  引入 `(liii time)` 时间 API。

## 2026-10-20 任务描述

### What

1. 建立任务 052 文档（本文件），明确现状、时钟来源复核、改动范围与 7 条验收点；
2. 复核底层时钟：确认 `time-utc->time-monotonic` 只是类型转换，真正单调来源是
   `(scheme time) monotonic-nanosecond` / `(current-time 'time-monotonic)`；
   因 039 禁止 `(liii time)` 除 `sleep`，选定 `(scheme time)` 作为 date-time
   内部时钟源；
3. 规划 TDD 与回拨验证路径，待开发阶段实施代码与测试。

### Why

039 将 pi 的时间函数统一到 `(liii date-time)` 后，超时仍以墙钟差值为基准。
墙钟受 NTP 回拨影响：`(- now last-act)` 可能为负，`(> ... idle)` 永不成立，
流式空闲超时与会话超时都可能静默失效。改用单调钟后，时间差只增不减，
回拨不再影响超时触发；墙钟继续只做时间戳展示，职责分离。

### How

- 在 `(liii date-time current-time)` 内基于 `(scheme time) monotonic-nanosecond`
  新增毫秒/秒接口，保持精确整数；
- `pi/time.scm` 暴露 `pi-current-monotonic-seconds`，agent 与三路 stream 的
  超时比较切换到该函数；
- 先写 date-time/pi 封装/超时判定测试，再实现；回拨场景优先用可注入时钟验证，
  无法真实改系统时钟时以静态门禁 + 单调性测试作为证据；
- 提交前依次通过 build、fmt、diff、check、doc 与相关测试。

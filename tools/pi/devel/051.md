## 任务背景

`PI_PLAN.md` §3 任务表 051 原文：

> 全量回归 `bin/gf test tools/pi/tests/liii/` 恒有 1 项失败：
> `tests/liii/pi-config-test.scm` 读取本机 `~/.pi/agent/models-store.json`
> （deepseek `base-url` 实为 `https://api.deepseek.com/anthropic`），与用例期望
> `https://api.deepseek.com` 不符——环境依赖导致每次验收都要维护「已知失败白名单」；
> 需改用 `PI_CODING_AGENT_DIR` 指向 `tools/pi/tests/fixtures/` 下的自建 fixture，
> 使全量回归真正全绿、验收脚本不再需要失败白名单；TDD 覆盖。

## 根因取证（2026-10-20 实测）

### 1. 全量回归基线

```
timeout 300 bin/gf test tools/pi/tests/liii/
  Total:  270
  Passed: 269
  Failed: 1
  Failed Test Files:
    tests/liii/pi-config-test.scm
```

（270 个测试文件，实测热缓存耗时约 15 秒；唯一失败文件即任务表所指文件。）

### 2. 唯一失败断言

`tools/pi/tests/liii/pi-config-test.scm:193`（用例 10：deepseek 默认模型元数据）：

```
(cdr (assoc 'base-url meta)) => https://api.deepseek.com/anthropic ; *** failed ***
; expected result: https://api.deepseek.com
; *** checks *** : 83 correct, 1 failed.
```

该用例的 env 为 `PI_CODING_AGENT_DIR=non_existent_dir_xyz` + `HOME=/non-existent`。

### 3. 真实根因（与任务表描述有出入，需在实施时按此办理）

**并非**读取本机 `~/.pi/agent/models-store.json` 所致：

- 该用例已把 `PI_CODING_AGENT_DIR` 指向 `non_existent_dir_xyz`，
  `pi-build-models-catalog`（`tools/pi/liii/pi/models/catalog.scm`）只读
  agent-dir 下的 `models.json` / `models-store.json`，两者都不存在 → 目录退化为
  **纯内置目录**；
- 内置 deepseek 模型的 `baseUrl` 是 `https://api.deepseek.com`
  （`tools/pi/liii/pi/models/builtin/deepseek.scm`）；
- 而 `pi-resolve-model-metadata`（`tools/pi/liii/pi/models/meta.scm`）有一条
  **刻意的归一化**：deepseek 的 `https://api.deepseek.com` 一律改写为
  anthropic 兼容端点 `https://api.deepseek.com/anthropic`（`norm-url` 分支），
  与本机 `~/.pi/agent/models-store.json` 中的取值恰好一致；
- 同一归一化在 `tools/pi/tests/liii/pi/pi-resolve-model-metadata-test.scm:77`
  已有**正确**断言。

⇒ 该断言是**历史遗留的陈旧期望值**，与当前生产语义（deepseek 一律走
`/anthropic` 端点）不符；生产代码行为正确，**不应为了迁就用例而回退归一化**。

**环境无关性验证**（把真实环境全部指空后复跑，失败完全一致）：

```
timeout 300 env HOME=/nonexistent-home PI_CODING_AGENT_DIR=/nonexistent-agent-dir \
  bin/gf test tools/pi/tests/liii/pi-config-test.scm
; (cdr (assoc 'base-url meta)) => https://api.deepseek.com/anthropic ; *** failed ***
; *** checks *** : 83 correct, 1 failed.
```

⇒ 属**恒定失败**（每次验收都要挂白名单的直接原因），而不是「有时绿有时红」。

### 4. 真实存在的环境依赖隐患（本次一并消除）

| # | 隐患 | 位置 | 触发条件 |
|---|---|---|---|
| E1 | 相对路径 `non_existent_dir_xyz` 依赖当前工作目录 | `tools/pi/tests/liii/pi-config-test.scm`（4 处）、`tools/pi/tests/liii/pi-cli-e2e-test.scm` | 机器上/工作目录下恰好存在同名目录 → 读到意外配置 |
| E2 | `pi-get-agent-dir` 在未显式传目录时回退到**真实进程环境** `PI_CODING_AGENT_DIR`，再回退 `~/.pi/agent` | `tools/pi/liii/pi/config.scm`（`pi-get-agent-dir`）、`tools/pi/tests/liii/pi/pi-get-agent-dir-test.scm` | 开发者 shell 里 `export PI_CODING_AGENT_DIR=...` → 该用例断言的 `~/.pi/agent` 后缀失效 |
| E3 | `lookup-env-var`（`tools/pi/liii/pi/template.scm:48`）与 `%safe-lookup-env`（`tools/pi/liii/pi/models/route.scm`）在 env 表为**空表 `'()`** 时回落到**真实进程环境** | `tools/pi/tests/liii/pi/pi-resolve-model-metadata-test.scm`（大量 `'()` 调用）、`pi-route-provider-and-model-test.scm` | 本机实测 export 了 `ANTHROPIC_BASE_URL=https://open.bigmodel.cn/api/anthropic`、`ANTHROPIC_AUTH_TOKEN`、`ANTHROPIC_DEFAULT_SONNET_MODEL=glm-5-turbo`；换机器（如 `GF_PI_BASE_URL`/`DEEPSEEK_BASE_URL` 被设置）即可能翻红 |

E1–E3 说明：任务表「环境依赖导致每次验收都要维护白名单」的判断方向正确，只是
**直接失败的那一条断言另有根因**（陈旧期望值）。本次任务把两者一并收敛。

## 实施路径（裁定）

1. **env 隔离哨兵**：`lookup-env-var` / `%safe-lookup-env` 以
   `(pair? custom-env)` 判定是否回落真实环境，故**空表 `'()` 会读真实环境**，
   而**非空但不含目标键的表不会**。测试侧统一改用「哨兵 env 表」——例如
   `(("__PI_TEST_NO_ENV__" . "1"))`——即可在不触碰生产代码的前提下做到
   「不查真实环境」；`resolve-pi-config` / `pi-resolve-model-metadata` /
   `pi-route-provider-and-model` 的调用一律传非空 env 表。
2. **fixture 布局**：
   - `tools/pi/tests/fixtures/config/`：钉死 deepseek `base-url`（= 生产归一化后的
     `https://api.deepseek.com/anthropic`）、`contextWindow`、`maxTokens`，
     以及 glm / kimi-coding 端点；`auth.json` 只放 google api_key，
     anthropic 凭据改由显式 env 注入（避免 `$VAR` 插值再引入一层环境耦合）；
   - `tools/pi/tests/fixtures/config-empty/`：`settings.json` = `{}`，
     无 `auth.json` / `models.json` / `models-store.json` → 语义等价
     「无用户配置」，用于替代 `non_existent_dir_xyz`；
   - fixture 路径沿用既有约定（先判 `tests/fixtures/...` 再判
     `tools/pi/tests/fixtures/...`），兼容 `bin/gf test` 与 `cd tools/pi` 两种跑法。
3. **用例改写**：`pi-config-test.scm` 中 4 处 `non_existent_dir_xyz` → fixture 路径；
   deepseek `base-url` 期望值改为 fixture 钉死值；每处调用补齐非空 env。
4. **防回归断言**：在三个函数级测试文件里补「污染环境不变性」断言，
   `putenv`/`unsetenv` 成对使用，确保不污染同进程内其它用例。

## 2026-10-20 任务描述

### What

1. 建档任务 051（文档阶段完成）；
2. 完成根因取证：全量回归基线（270/269/1）、唯一失败断言定位、陈旧期望值的真实
   根因（deepseek base-url 归一化）、环境无关性复验（换 HOME/agent-dir 失败一致）、
   以及 E1–E3 三类真实环境依赖隐患；
3. 裁定实施路径：纯测试侧改动 + 自建 fixture + env 隔离哨兵 + 污染环境防回归断言，
   生产代码零改动。

### Why

验收脚本长期维护「已知失败白名单」有两个坏处：其一，掩盖真实回归（白名单里的文件
即使新增失败也不会报警）；其二，掩盖环境依赖——用例断言值随本机
`~/.pi/agent/` 配置漂移，换机器即翻红。全量回归必须**真绿且与环境无关**，
才能作为后续任务的可靠门禁。

### How

1. 以「fixture 钉死期望值」替代「读本机配置推断期望值」：把 deepseek 端点等
   期望值写进 `tools/pi/tests/fixtures/config/`，用例断言与 fixture 一一对应；
2. 以「哨兵 env 表」替代「空 env 表」：利用 `lookup-env-var` /
   `%safe-lookup-env` 的 `(pair? custom-env)` 判定语义，传非空但不含目标键的表，
   即可在不改生产代码的前提下阻断真实进程环境回落；
3. 以「仓库内 fixture 路径」替代「相对 cwd 的假路径」：消除 E1；
4. 以「污染环境不变性断言」做 TDD 防回归：`putenv` 注入污染值 → 断言解析结果不变
   → `unsetenv` 还原。

## 复现证据与根因分析（Claude 实测数据留证）

根据 `tools/pi/devel/064-repro/` 与实测连拍脚本 `tools/pi/devel/064-capture.py` 的取证：

1. **真实 Windows Terminal 瞬时空白现象留证**：
   - 运行环境：Windows 11，Windows Terminal 最大化窗口，运行 `bin/gf demo/tui/snake.scm`；
   - 抓取方式：`064-capture.py` 以约 15～16 fps 进行高频窗口图像截取分析；
   - 统计结果：在 4 秒 61 帧中，精准捕获到 **10 次整行瞬时空白事件**（每次持续约一帧，约 65ms）；
   - 空间定位：整行空白固定发生在 `y=271..308` 区域（右侧 STATS 计分卡的心跳行 `⠋ Heartbeat` 所在位置）；
   - 墨迹量对照：该区域在空白帧的前后两帧墨迹量均为 125/126 像素，而在空白帧完全降为 0 像素；
   - 时间频率：约每 7 帧（约 450ms）捕获到一次中间态，与 Heartbeat 行的刷新节奏相关；
   - 证据文件：留档于 `tools/pi/devel/064-repro/`，含三帧拼图 `flicker-triptych.png`（清晰展示 before 有文字、blank 整行变黑、after 恢复文字）。

2. **机制证据（ANSI 写入流与中间态重现）**：
   - 截取 3 秒内 28 个渲染帧的原始 ANSI 字节流，共出现 **53 次**如下操作模式：
     ```text
     CUR(row,1)  ESC[2K\r  CUR(row,1)  <新行文本>
     ```
   - 根因分析：
     - **直接根因 1（清行导致的空白中间态）**：`goldfish/liii/tui/main-screen/driver.scm` 中对变化行的渲染逻辑为：
       ```scheme
       ((or (eq? type 'update) (eq? type 'append))
        (terminal-set-cursor! term 0 idx)
        (terminal-clear-line term)       ; 写入 ESC[2K\r 清空整行
        (terminal-set-cursor! term 0 idx)
        (terminal-write term (diff-op-text op)) ; 写入新文本
       )
       ```
       清空整行与写入新文本是两次独立的 I/O。终端如果在 `terminal-clear-line` 与 `terminal-write` 之间触发了绘制周期（paint cycle），用户视觉上就会看到整行（包括框线与文字）瞬时全黑消失！
     - **逐写入重绘模拟器验证**：将截获的 ANSI 操作流按写入原子逐步快照到虚拟屏幕，28 帧中在被更新行上共产生 **40 次完全空白的中间快照**，证实该逻辑在理论和模拟器中必然造成空白窗口期；
     - **诱因 2（频繁无意义的光标控制）**：每帧无条件调用 `(terminal-hide-cursor! term)`，28 帧发送了 28 次 `ESC[?25l`，不仅增加 I/O 碎片，还促使控制台引擎重置光标渲染状态；
     - **诱因 3（无同步输出包裹）**：多条 ANSI 命令作为分散小片段直接输出，没有用现代终端标准的同步渲染指令保护，终端渲染线程随时可能在帧中间介入。

## 改动范围与详细方案

### 1. 原地覆写（In-place Overwrite）消除清空

- 在 `goldfish/liii/tui/main-screen/driver.scm` 的 `screen-render!` 中，重构 diff-ops 处理逻辑：
  - 对于 `'keep`：保持零操作；
  - 对于 `'update` 或 `'append`：
    - 直接移动光标到行首：`(terminal-set-cursor! term 0 idx)`；
    - 写入新内容：`(terminal-write term new-text)`；
    - **彻底移除前置 `(terminal-clear-line term)`**；
    - **清除行尾判定**：比较新行与旧行的显示宽度 `(display-width)`。如果 `(< (display-width new-text) (display-width old-text))`，则在写入新内容后，调用 `terminal-clear-line-to-end`（发送 `\x1b;[K`），仅擦除旧行尾部残留的字符；若新行宽度大于等于旧行，则无需任何清除操作，完全原地覆写；
  - 对于 `'clear`（行被删除）：
    - 定位光标：`(terminal-set-cursor! term 0 idx)`；
    - 清除整行：`(terminal-clear-line term)`。
  - 旧行文本不在 diff-op 中携带，driver 从 `old-lines` 按 idx 读取；`'append` 的旧宽度按 0 处理。

### 2. 终端能力扩展：行尾清除与同步输出（DECSET 2026）

- 修改 `goldfish/liii/tui/terminal/protocol.scm`、`standard.scm`、`virtual.scm`：
  - 新增协议方法：
    - `terminal-clear-line-to-end`：清除光标至行尾（ANSI 序列：`\x1b;[K`）；
    - `terminal-begin-sync!`：开启终端同步输出（ANSI 序列：`\x1b;[?2026h`）；
    - `terminal-end-sync!`：结束终端同步输出（ANSI 序列：`\x1b;[?2026l`）；
  - `standard-terminal`：向当前输出端口输出对应转义序列；不支持 DECSET 2026 的终端会安全降级忽略；
  - `virtual-terminal`：在 `vt-raw` 原始流中记录这些 ANSI 序列，并在 `virtual-terminal-screen` 中正确模拟 `clear-line-to-end` 行为（把光标以后的字符空格化）。

### 3. 按需切换光标可见性（Smart Cursor Visibility）

- 在 `standard-terminal` 与 `main-screen` 中跟踪当前光标的可见状态：
  - 仅当目标状态与当前状态不同时（例如原本显示、现需隐藏，或反之），才发送 `\x1b;[?25l` 或 `\x1b;[?25h`；
  - 杜绝每一帧无条件重复发送 `terminal-hide-cursor!`。

### 4. 同步帧包裹与统一刷新

- 在 `screen-render!` 的绘制块首尾加入同步锁：
  ```scheme
  (when has-changes
    (terminal-begin-sync! term)
    ;; 遍历渲染 diff-ops（原地覆写 + 尾部擦除）
    ...
    (terminal-end-sync! term)
    (terminal-flush term)
  )
  ```
- 确保所有写入作为一个原子批次提交给终端，并在物理刷新前关闭同步模式，彻底消除撕裂与局部重绘。

### 5. 虚拟终端与逐写入模拟器自动化断言

- 编写/更新单元测试：
  - 更新 `tests/liii/tui/main-screen/` 相关测试用例；
  - 新增 ANSI 流断言测试：
    - 断言更新行只包含光标定位与文本写入，不存在「`\x1b;[2K\r` 紧跟文本写入」；
    - 断言新旧行等宽时无 clear 序列；
    - 断言新行缩短时在尾部出现 `\x1b;[K`；
    - 断言每帧 `\x1b;[?2026h` 与 `\x1b;[?2026l` 成对出现；
    - 断言在连续多帧渲染中不会重复发送 `\x1b;[?25l`；
  - 实现「逐写入重绘模拟器」测试：模拟原子写操作，断言无论何时截取虚拟屏幕，被更新行都不会变成全空行。

### 6. 真实终端实机复测

- 执行 `python3 tools/pi/devel/064-capture.py --seconds 4`；
- 验证在相同条件下（Windows Terminal 最大化运行 4 秒，约 60 帧连拍），报告 **0 次 blank-band events**；
- 确认闪烁彻底消除。

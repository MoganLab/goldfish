步骤描述是**纯文件名启发式**（不读文件内容）：`test`/`spec` → `Test file for X`；
`index.ts|js` → `Entry point for X module`；含 `config` → `Configuration: X`；
`route`/`router` → `Routing: X`；`middleware` → `Middleware: X`；
`model`/`schema` → `Data model: X`；`service` → `Service: X`；
`controller`/`handler` → `Handler: X`；`util`/`helper` → `Utility: X`；
其余 → `X module`。

步骤收集范围：主题目录（或 `src/<topic>`）下深度 ≤3 的源文件，最多 15 个；
源扩展名白名单 `.ts .tsx .js .jsx .py .go .rs .java .rb .php .ex .exs .kt .swift
.c .cpp .h .yml .yaml .toml .json`；`testing` 主题额外收集测试目录（每目录最多 5 个），
`ci` 主题额外收集 `.github/workflows/*` 与 `.gitlab-ci.yml`/`Jenkinsfile`。

### 实测缺陷（五条，均有源码/实测依据）

1. **print 模式空输出**：`pi -p "/onboard"`、`pi -p "/tour"`、`pi -p "/tour testing"`
   三条实测均 **退出码 0、stdout 0 字节、stderr 空**。扩展用
   `pi.sendUserMessage(..., {deliverAs: "followUp"})` 派发内容（★ `onboard-command.ts` /
   `tour-command.ts`），print 模式不等待异步 follow-up 回合；连 `/tour` 的
   `ctx.ui.notify` 通知在 print 模式下也被吞掉（与 044 偏差 #15、045 偏差 #17、
   046 偏差 #21、047 偏差 #27 同源）。
2. **缓存陈旧（深度 2 的改动不失效）**：内容哈希只覆盖「若干 manifest 文件内容 +
   根目录清单」（★ `codemap-generator.ts` `HASH_FILES` / `computeContentHash`），
   而 codemap 的目录树覆盖**深度 2**。实测：新增 `src/brand-new.js` 后再跑
   `/onboard`，返回的仍是**旧地图**（不含该文件），只有 `/onboard --refresh`
   才更新（★ `onboard-command.ts` 命中内存缓存即直接返回，不重算）。
3. **tour 缓存同样陈旧**：tour 缓存键是 codemap 的 `contentHash`（★
   `tour-generator.ts` `getOrGenerateTour`），受缺陷 2 影响，代码变了 tour 不变。
4. **死代码**：`stale` 标记**永远为 false**（★ `index.ts` / `onboard-command.ts` /
   `onboard-tools.ts` 三处都写死 `stale: false`，无任何置 true 的路径），因此
   `> This codemap may be outdated. Run /onboard to refresh.` 永不出现；
   `CompassConfig`（`max_injection_chars` / `inject_on_first_turn` /
   `cache_enabled`，★ `types.ts`）从未被读取，注入上限写死在
   `DEFAULT_MAX_INJECTION_CHARS = 6000`。
5. **「必须在 git 仓库内」是假命题**：错误文案是
   `No project detected. Run from within a git repository.`，但
   ★ `project.ts` `detectProject` 在非 git 目录会**回退到 cwd**（id = cwd 路径哈希）。
   实测在非 git 目录 `/home/da/pi-compass-nogit` 跑 `/onboard` 正常产出 codemap。

### 其他实测观察（非缺陷但影响移植取舍）

- **扩展生态互相污染**：本机同时装着 pi-blueprint / pi-red-green 等扩展，
  `/onboard` 触发的模型回合里，模型会顺带调用 `blueprint_status` 等无关工具，
  系统提示词也被别的扩展注入的内容污染（实测 assistant 文本提到
  `Active Blueprint: "Approval probe"`）。对照时须用 `--no-tools` 或人工甄别。
- **codemap 对非 JS 生态几乎为空**：包/框架检测只认 npm/go/cargo/pip/poetry/
  composer/gradle/maven；Scheme 工程（如本仓库）既无 manifest 也无依赖，
  `### Packages` / `### Frameworks` 两节直接省略。
- **tour 的源扩展名白名单不含 Scheme**：白名单里没有 `.scm`，因此在 Scheme 工程里
  `/tour <topic>` 恒为 `No files found for topic "...".`（tour 生成只看文件名与目录，
  与文件内容无关）。
- **tour 主题只在根目录与 `src/` 下找**：★ `tour-generator.ts` `buildTourSteps`
  只试 `<root>/<topic>` 与 `<root>/src/<topic>`，工程内更深层的主题目录找不到。
- **目录树深度固定 2**、忽略清单固定（`node_modules .git dist build .next .nuxt
  __pycache__ .tox .mypy_cache .pytest_cache target .gradle .idea .vscode vendor
  coverage .turbo .cache`），点目录一律跳过（`.github` 例外）。

## 形态裁定

脚本模式无 TUI、无斜杠命令、无 `~/.pi/compass/` 共享目录，但 compass 的核心价值是
**「结构化 codemap + code tour 让模型少走弯路」**——它既要在**无人值守的脚本里**
直接产出可读的地图/导览，也要在**普通会话里**把地图注入系统提示词以省 token。
裁定如下。

### 1. 命令面：2 个斜杠命令 → 2 个 CLI 开关

```bash
# 生成（或复用缓存）codemap，Markdown 写 stdout（等价 /onboard）
bin/gf pi --codemap

# 强制重新生成（等价 /onboard --refresh）
bin/gf pi --codemap --refresh

# 列出可用 tour 主题（等价 /tour 无参数）
bin/gf pi --tour

# 打印指定主题的 code tour（等价 /tour <topic>）
bin/gf pi --tour src
```

互斥与前置（`compass/args.scm` 校验，报可读错误并退出码 1）：

- `--codemap` 与 `--tour` 互斥（一次调用只做一件事）；
- `--codemap` / `--tour` 与 `--code-review` / `--simplify` / `--red-green` /
  `--blueprint` / `--plan-*` 互斥（同一轮只能有一种工作流，对齐 046/047 的既有校验风格）；
- `--refresh` 只允许与 `--codemap` 同用（tour 实时计算，无缓存可刷新）；
- `--codemap-file <path>` 只允许与 `--codemap` 同用（tour 不落盘）；
- `--tour` 的主题取其后**第一个既不以 `-` 开头也不以 `@` 开头**的参数；
  没有则视为「列主题」（对齐 `--list-models [search]` 的可选值风格）；
- `--codemap` / `--tour` **不需要模型凭据**（纯本地静态分析），不进入 provider 流程。

### 2. 落盘位置：工程内 `.pi/codemap.json`，不写 `~/.pi/`

- 机器可读状态：`.pi/codemap.json`（唯一真相源，形态对齐 native 的 `codemap.json`：
  `data` + `contentHash` + `createdAt` 三段结构）；
- 路径可用 `--codemap-file <path>` 覆盖（便于测试用临时目录）；
- **tour 不落盘**：tour 是 (root, topic) 的纯函数，实时计算，杜绝 native 的
  tour 缓存陈旧（实测缺陷 3）；
- **绝不写 `~/.pi/` 任何目录**（native 写 `~/.pi/compass/`，与原生 pi 共存时会互相
  污染；本项目对 `~/.pi/agent/` 一直保持只读复用约定，不应例外）。

### 3. 缓存与新鲜度：哈希覆盖 codemap 实际内容（修 native 缺陷 2）

- 内容哈希 = **深度 2 目录树 + 各 manifest 文件内容**的摘要——即 codemap 真正
  依赖的输入，而不是 native 的「根目录清单 + 固定 manifest 列表」；
- 命中条件：缓存存在且哈希与当前工程一致 → 复用（`### Generated` 时间戳保持不变）；
  否则重新生成并落盘；
- `--refresh` 无条件重新生成；
- 效果：native 的「深度 2 改了但 `/onboard` 仍给旧图」不再发生（**改进，非对齐**）。

### 4. 检测器：移植 native 七件套 + Scheme 适配

七个检测器按 native 语义移植（目录树 / 包 / 框架 / 入口 / 构建脚本 / 约定 / 关键文件），
规则表（框架 43 条、入口点常见清单、约定文件清单、关键文件清单、npm scripts 白名单、
目录忽略清单）逐条对齐；在此之上做**三处 Scheme 适配**（否则本仓库上 codemap 几乎是空的）：

1. **tour 源扩展名**加 `.scm` / `.sld` / `.ss`（否则 Scheme 工程恒无 tour）；
2. **入口点**加「Scheme 库目录」规则：深度 ≤2、目录名属于
   `liii` / `scheme` / `srfi` / `lib` / `libs` / `src` 且含 `.scm` 文件 → kind `library`；
   `xmake.lua` → kind `config`；
3. **构建脚本**加 `xmake.lua` → `xmake build`（native 只认 npm/Makefile/CI/Docker）。

包/框架检测维持 native 的多语言清单（npm / go / cargo / pip / poetry / composer /
gradle / maven + 43 条框架规则）；Scheme 工程无 manifest 时这两节自然为空。

### 5. tour 主题解析：全树搜索（修 native 的「只看根与 src」限制）

- 主题目录 = codemap 目录树中**名字等于主题的目录**（深度 ≤2，按路径排序取首个）；
  无同名目录时退回 native 的 `<root>/<topic>` / `<root>/src/<topic>`；
- 特殊主题沿用 native：`testing`（测试目录）、`ci`（`.github/workflows` 等）、
  `database`（迁移/ORM 目录）；
- 步骤收集：主题目录下深度 ≤3 的源文件，最多 15 个；步骤描述沿用 native 的文件名
  启发式（`test`/`spec`/`index`/`config`/`route`/`middleware`/`model`/`schema`/
  `service`/`controller`/`handler`/`util`/`helper`），`.scm` 文件同样适用
  （`foo-test.scm` → `Test file for foo`）。

### 6. 系统提示词注入（省 token 的主战场）

- 若 `.pi/codemap.json` 存在且哈希与当前工程一致 → 把 codemap Markdown
  **截断到 6000 字符**（同 native 的 `DEFAULT_MAX_INJECTION_CHARS`）追加到系统提示词，
  每会话一次；
- 截断提示沿用 native 形态，但把命令名换成脚本模式：
  `... (codemap truncated, run --codemap to see full output)`；
- **不移植 native 的 stale 提示**（native 的 `stale` 恒为 false，是死代码）；
  脚本模式用哈希保证新鲜度；
- 逃生舱：`--no-codemap-inject` 关闭注入；
- **无缓存即不注入** → 未跑过 `--codemap` 的工程行为零变化。

### 7. 内置工具

保留 native 的两个工具（`codebase_map` / `code_tour`），形态对齐：

| 工具 | 入参 | 返回 |
|---|---|---|
| `codebase_map` | 无 | codemap Markdown 全文（顺带刷新缓存） |
| `code_tour` | 可选 `topic` | 无 topic → 主题列表；有 topic → tour Markdown |

- 两个工具**默认注册**（对齐 native：模型随时可拉地图/导览）；
  `--exclude-tools codebase_map,code_tour` 或 `--no-tools` 可关闭；
- 显式给出 `--tools` 白名单时**不自动追加**（白名单即用户意图；需要时显式写
  `--tools read,codebase_map`）——这一点比 native 更严格，是有意收紧；
- 两个工具**不进 `PI_ALL_TOOL_NAMES`**（与 `tdd_*` / `blueprint_*` 同款约定：
  工作流工具不占可选工具清单），既有 `pi-tools-basic-test.scm` 的
  `(length PI_ALL_TOOL_NAMES) => 8` 断言不受影响。

### 8. 输出形态

- print 模式：`--codemap` / `--tour` 的 Markdown **写 stdout**（修 native 的 print
  空输出缺陷，实测缺陷 1）；
- JSON 模式：stdout 保持**纯 JSONL**（既有事件序列完全不变），codemap / tour
  摘要写 **stderr**（对齐 045/046/047 的 stdout/stderr 分流）；
- `--codemap` / `--tour` **不调用模型** → 不产生 agent 事件流（无凭据也能跑）。

### 9. 安全与既有规范

- 所有文件读取有路径边界（只读工程内文件，不跟随工程外的软链）；
- 状态只写工程内 `.pi/codemap.json`，**不写 `~/.pi/` 任何目录**；
- 日志不写凭据；codemap 内容只含文件名与 manifest 摘要，不含源码正文
  （约定文件除外，截断 2000 字符，与 native 一致）；
- 无凭据 / 超时 / 网络失败按既有错误规范报错并退出码 1（本任务两条流程不触网）；
- 单文件不超过 300 行（`bin/gf check` 硬约束），子库再拆子模块
  （如 `compass packages` 超限可拆 `compass packages npm` 等）。

6. **内置工具**：

   - JSON 模式：stdout 为纯 JSONL（既有事件序列不变），codemap / tour 摘要写 stderr；
   - `--codemap` / `--tour` 不调用模型 → 无 agent 事件、无凭据要求。
8. **边界与安全**：
